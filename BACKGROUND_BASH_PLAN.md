# Background Bash plan

## Goal and boundaries

Let managed root and worker agents launch a background shell, list jobs, get a job's status/output, and kill it. The router owns the process and its lifecycle. The default timeout is 10 minutes, with a per-launch override. On completion, notify the agent with the exit code when available. Show jobs in an agent header widget. Deny subagents access. All four operations are exempt from inline-tool restrictions and inline allowance accounting; launch must work with zero inline allowance. Bound polling, retained data, and cleanup.

Do not change foreground Bash behavior, impose new command-content restrictions, or treat background shells as subagents. Do not restore or depend on removed Pi integration. This document is a plan, not an accepted spec or implementation.

## Spec first

Before production changes, write `docs/specs/background-bash.spec.md` with the standard metadata, intent, invariants, Given/When/Then scenarios and an E2E verification matrix. Update `docs/specs/INDEX.md` and root `AGENTS.md` links as required. Backfill or update affected existing specifications before modifying their behavior. Keep the new spec Draft until its complete matrix passes.

Define and test these requested behaviors and necessary edge semantics:

1. **Launch:** root or worker agent supplies a shell command and optionally a timeout. The tool returns an identifiable job without waiting for command completion. Default timeout is 10 minutes; document timeout units and validate overrides. Use existing managed Bash working-directory and environment behavior where applicable; specify any necessary differences rather than inventing new restrictions. Report invalid input and process-start failures honestly.
2. **List/get/kill:** list and get return owner-scoped job state and available output; get returns the exit code when known. Kill stops the identified owned job. Specify running, successful, nonzero exit, killed, timed-out and uncertain outcomes without fabricating an exit code. Define repeated kill and completion races, unknown IDs and output truncation. Reads are snapshots, not blocking waits.
3. **Notifications:** on completion, notify the owning agent with the job ID and exit code when known, otherwise an honest status. Reuse the ordinary managed notification/wake path and its existing delivery behavior; do not add durable delivery or exactly-once guarantees.
4. **Authority and exemption:** derive root/worker/subagent identity and owner from the trusted managed binding, not tool arguments. Deny all four operations to subagents, including direct and alternate runtime dispatch, before effects. Fence operations and lifecycle updates to the correct owner/current authority; other agents and stale bindings cannot inspect or kill jobs. All four operations bypass inline-tool enablement and inline allowance, and never debit it. This exemption does not bypass owner fencing or the separate polling budget. Foreground tools retain their existing behavior.
5. **Polling budget:** list and get share a bounded per-owner/session-lane read budget, either by safely reusing the existing subagent read pool or by a separate pool modeled on it. An appropriate simple default is three credits, replenishing one per minute; list and running get cost one, terminal get is free. State the final choice in the spec. Atomic accounting must prevent alternating tools or concurrency from evading the budget. Exhaustion returns a clear message to await completion or do other work. Launch, kill and notifications do not consume polling credits; UI updates must not consume an agent's tool budget.
6. **Header widget:** show the selected agent's background jobs and status in a compact conversation header widget. Follow existing accessibility and design patterns and keep jobs scoped to the selected agent. Output and kill remain tool operations; do not add UI controls for them.

## Implementation

1. **Audit integration first.** Trace current managed tool registration, checked admission, root/worker/child identity, fences, ordinary Bash execution, process-group cleanup, notice delivery, existing state storage, WebSocket projections and header widget. Identify supported runtime adapters and implement through their existing checked paths. Do not rely solely on hiding tools from a subagent; server-side denial is required. Preserve unrelated changes and avoid changing retired components.
2. **Router-owned lifecycle.** Add a minimal router-owned job manager with owner-scoped state for snapshots; use existing storage only if needed. Do not add durable crash recovery or exactly-once execution guarantees. Use router-owned process handles/groups, validated process identity and existing cleanup machinery. A timeout or kill must terminate and reap the owned process tree, with bounded escalation and an honest outcome if cleanup or exit status cannot be established. Never signal a potentially reused PID without proof. Handle completion/kill/timeout races and use existing fencing and cleanup patterns for owner termination, shutdown and binding replacement; never assume a process can safely be signaled after its identity is lost.
3. **Bound resources.** Choose and document practical bounds for concurrent jobs, captured output, list/response size, and terminal record age/count, using existing project defaults where suitable. These are necessary implementation choices for bounded retention and cleanup, not additional user-requested product features. Drain output after the capture limit and visibly indicate truncation. Prune terminal records and associated output automatically on a defined trigger, including startup/periodic cleanup as needed. Use existing notification retention and delivery behavior. Release process handles, timers, pipes and reservations on every outcome; report capacity or storage failures instead of leaking resources.
4. **Tool integration.** Add launch/list/get/kill schemas and dispatch through checked managed authority. Explicitly exempt every operation from inline gates and allowance debit, rather than treating launch as inline Bash. Apply the bounded read budget only to list and running get. Use owner and fence validation before reads, process effects and notice publication. Reuse existing request handling where applicable without promising exactly-once launches.
5. **UI and transport.** Expose the owner-scoped job status needed by the widget using existing router transport patterns. Add typed UI validation and a compact, accessible header widget; do not add output or kill controls. Preserve permissive non-credentialed CORS for arbitrary frontend origins; never use Origin as identity or authorization.

Use deterministic local mock LLM/provider calls, isolated temp state and event-driven synchronization. Clean up all test processes and resources. Map each scenario below to a named Playwright test in the spec; supplemental unit tests are not a substitute. Be explicit if any scenario cannot traverse a boundary rather than claiming full acceptance.

| Scenario | Required E2E evidence |
| --- | --- |
| Launch and success | Root and worker agents each invoke the real tool, which returns before command completion; verify the 10-minute default deadline, real output and exit 0; job state, completion notice, WebSocket update and header all agree. |
| Nonzero exit and output | Actual shell produces stdout/stderr and exits nonzero; get shows the real exit code and bounded output, including truncation when applicable; the notification reports the exit code. |
| Timeout | Short override triggers timeout and process-tree cleanup; verify terminal state, notice and honest exit/signal. Validate malformed overrides and verify default is 10 minutes. |
| List, get and kill | Multiple owned jobs, running snapshots, tool kill, repeated kill and exit race; no unrelated process is stopped. |
| No inline restriction | With inline disabled and allowance at zero, actually launch, list, get and kill; confirm none debit inline allowance. Verify normal foreground Bash remains subject to its existing policy. |
| Subagent and ownership | Root and worker can use all four operations; actual subagent discovery and direct/alternate dispatch attempts for all four operations are denied without side effects; another owner and stale fence cannot read or kill a job. |
| Polling | Alternate list and running get and race concurrent calls; verify a shared bounded budget, exhaustion and refill, terminal get free, and launch/kill/notifications unaffected. If sharing the existing subagent pool, test cross-tool alternation and preserve its existing spec. UI events do not debit the tool budget. |
| Notifications | Completion uses the ordinary router notification path and reports the exit code when known; do not claim durable or exactly-once delivery. |
| Widget | Actual browser shows the selected agent's jobs and status; agent switching and live updates stay correctly scoped, and an arbitrary cross-origin frontend works through the proxy. No output or stop controls are required. |
| Bounds and cleanup | Exercise chosen concurrency, output and retention limits; automatic TTL/count pruning and artifact cleanup; active jobs and ordinary notifications follow their applicable policies; capacity is released after success, timeout, kill and failure. |
| Failure paths | Invalid input/cwd, spawn or applicable storage failure, notification failure and uncertain cleanup produce honest errors/state with no leaked process, reservation, fabricated exit code or unauthorized side effect. |
| Shutdown and ownership transition | Owner termination, router shutdown and stale-binding race exercise real process cleanup and fenced updates; never signal an unverified process after restart. |
