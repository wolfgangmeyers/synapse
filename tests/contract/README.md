# Real Claude CLI isolation experiment

Run `MECHA_RUN_REAL_CLAUDE_CONTRACT=1 tests/contract/run-claude-isolation.sh` on Linux with bubblewrap, Python 3 and Claude Code **2.1.316** installed. Without opt-in it skips. Missing isolation, an unexpected network namespace/interface/route, failed local provider exchange, unsupported version, or a failed assertion exits nonzero. The wrapper never falls back to an uncontained invocation.

Bubblewrap creates fresh network, user, PID and other namespaces; the sandbox exposes only system binaries/libraries, the CLI binary, the test script, a temporary filesystem, private `/proc` and `/dev`. It does not expose the host home, runtime socket directories or inherited environment. The test verifies the network namespace differs from the caller, has only loopback and no external route; an unroutable documentation address is used for a no-route positive check. It starts a deterministic HTTP provider on literal `127.0.0.1` inside that namespace, with a synthetic API key and temporary HOME. There are no real provider calls or credentials. The network namespace and filesystem boundary depend on the host kernel and bubblewrap being trustworthy; this is not a defense against a compromised kernel, bubblewrap, system libraries or CLI binary.

On this host, `unshare -Urn` and `unshare -n` failed with operation not permitted, but bubblewrap created a different network namespace with only loopback and no external route. On 2.1.316 the provider received requests and returned the fixed answer. The positive control exposed `Bash`; `--tools '' --strict-mcp-config` exposed no tools. With a synthetic user-level stdio MCP server configured in the temporary home and `--tools ""`, the non-strict positive control started the server, issued `tools/list`, and advertised its canary. Adding `--strict-mcp-config` produced no server startup or advertised tools. All runs completed. No LLM or external service was contacted. The test inspects actual outbound provider requests, not just CLI help or process arguments.

The local provider also returns a forged `Bash` tool-use response containing a command that writes a marker in the sandbox. Both runs use `--permission-mode bypassPermissions`: with `--tools Bash` the marker must exist; with `--tools ''` it must not. The provider injects only for the exact test user prompt. Each run must complete a mock exchange and make a subsequent request containing the forged assistant Bash tool use followed by a matching user `tool_result` for `toolu_test123`; a response send alone is not evidence of consumption. The marker is removed before each run, and the private tmpfs is discarded when bubblewrap exits.

**Limitations:** This checks one forged Bash response and builtin tool advertisement for these CLI invocations, not general resistance to malicious providers or tool calls, managed settings, hooks, plugins, router integration, or other MCP configuration sources. The MCP comparison covers only this user-level stdio configuration with no explicit `--mcp-config`; it is not a general proof of `--strict-mcp-config` enforcement. It does not prove isolation on other hosts or versions. A failing or skipped run is not evidence of enforcement. Do not treat this as acceptance of the complete Claude worker isolation contract. Keep the broader sidecar inventory and behavioral specs aligned when those gaps are tested; they may be edited by concurrent work, so this experiment does not overwrite them.

This is an opt-in, host-dependent experiment, not part of the deterministic default E2E suite. Historical observations above are not results for every checkout or host. Inspect the script and sandbox prerequisites before opting in; no run is implied by inclusion in a patch.
