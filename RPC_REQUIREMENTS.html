Confirmed direction

Product brief

Router-managed Pi RPC requirements

Build an alternative way to run workers and the supervisor. In this brief, RPC means the router starts Pi directly and communicates with it without a terminal window. This is direction for investigation and product planning. It is not a validated technical design.

Tmux is the supported legacy compatibility path for this delivery. Its future deprecation and removal are direction, not implementation scope here unless another confirmed requirement already requires them.

Research Specification
01

Known direction

Settled
  • The router exposes an API that launches a new agent.
  • The router never launches a tmux agent.
  • A user may still launch Pi inside tmux. Outside RPC mode, when the mecha-messaging extension is installed and active, Pi automatically connects to the router through the current protocol.
  • The existing tmux path stays supported and fully working as the legacy compatibility path alongside the new RPC system for this delivery.
  • Tmux and router-managed agents can send messages to each other through the router.
  • Router-managed Pi agents load a dedicated thin extension that registers their router-backed tools. Its code is fixed and generic; it does not hardcode router tool definitions. They do not use the existing mecha-messaging or mecha-goal extensions. Tmux agents keep those extensions and the current protocol.
  • Accepted decision — Wolfgang override: the wolfgangmeyers/pi-packages fork’s main branch is the pi-subagents source of record. Phase 1 runs the package’s existing checks and build:types from that workspace, then uses its package-declared ./src/index.ts extension entry in the isolated stock Pi 0.85 proof. It does not require package publication, a registry pin, release metadata, or a changelog. The proof still uses installed Pi, not local Pi-core source.
  • The router owns router-managed process lifecycle, RPC supervision, histories, Web UI state and controls, message routing, and every other capability required by this brief.
  • Business, state, and tool behavior lives in router internal handlers. The thin extension registers tools and bridges control traffic. It does not duplicate router behavior.
  • The thin extension registers every router capability in the selected inventory of up to 32 tools. The exhaustive parity inventory is research evidence, not a scope limit. An omitted inventory row does not remove a required capability.
  • Pi independently verifies late extension-tool registration: a tool registered through an RPC-invoked extension command appears with its exact supplied schema on the next model request. This proves Pi registration only. It does not prove the complete production router executor or result path.
  • After a router-managed process starts and before its first model turn, the router sends one bounded, versioned, canonically hashed dynamic-tool manifest through the reserved RPC-invoked extension command. The agent is not ready until the full manifest validates and registers successfully for its current extension runtime generation.
  • The extension constructs and registers every manifest tool. The router owns each tool name, description, input schema, handler mapping, and handler logic. A desired manifest has 16–32 definitions: revision one starts with the 16 exact baseline tools. Adding a router tool within that selected limit does not require an extension code change.
  • The extension enforces byte bounds on raw untrusted manifest input before parsing. It validates the parsed manifest and every schema node before coercion or registration. It builds schemas from that validated subset and rejects coercive values, unsupported types or constructs, unsupported or type-inappropriate keywords, reversed ranges, and any unbounded accepted string, array, integer, or number.
  • The extension preflights the entire manifest atomically before exposing a manifest tool. It rejects malformed JSON; duplicate or conflicting manifest names; names already present in pi.getAllTools(), including built-ins, reserved names, and existing extensions; unsupported protocol versions; excessive bounds or nesting; hash or runtime-generation mismatches; and unsafe property names. A rejected startup manifest leaves the agent not ready. A rejected later update leaves the current tool set unchanged. Both leave no partial manifest-tool registration and record the failure in complete history.
  • Every installed manifest name is immutable for that extension runtime. Dynamic registration is add-only for a running process. Until a separately accepted add-only update protocol passes its acceptance checks, the extension accepts exactly one startup manifest and rejects delivery after the first non-command prompt. That protocol may add a previously unused name if supported. It cannot remove, replace, or mutate an existing tool definition in place, and it never treats active-tool deactivation as registry removal or reconciliation.
  • A changed schema or meaning gets a new permanently unique Pi-visible name: <capability_id>__<definition_sha256>, tied to its full canonical definition hash. It takes effect only by restarting the Pi process on its same Pi session and delivering the new full manifest before work resumes. A session switch, reload, resume, or fork creates a fresh extension runtime generation and also replays the full manifest before a model turn. This is not a context reset.
  • Each generic tool closure captures immutable trusted runtime generation, manifest hash, tool name, and allowlisted operation. It preserves the exact dynamically registered tool name and validated arguments in one dedicated router control request. It revalidates policy before every side effect and never relies on Pi coercion to distinguish primitive types. Manifest data never provides code, URLs, headers, shell commands, credentials, or executable identifiers.
  • Initial acceptance still requires complete parity for all 16 required tools. The dynamic manifest is the registration mechanism, not a scope reduction.
  • A dynamic tool returns only its bounded immediate asynchronous result. A later result or error uses the separately validated control-delivery mechanism and cannot replace the original Pi tool result. Full router end-to-end dispatch, result delivery, ordering, replay, and stale-generation handling remain acceptance work.
  • The router keeps state wherever possible.
  • Each router-managed Pi process gets a generated session ID when it starts. The ID lives for the lifetime of that agent.
  • Restarting an agent resumes the same Pi session.
  • After the router itself restarts, every agent that was running comes back automatically and resumes the same Pi session.
  • Reset context is a separate action. It keeps the worker name and both Web UI histories. It creates a new Pi session ID. Later restarts resume that new session.
  • Terminating an agent clears its router state.
  • The router automatically restarts a crashed agent. It stops after a bounded number of repeated crashes so it cannot restart forever.
  • A usable product will need substantial implementation work.
  • The router keeps internal source and runtime metadata for each agent. It owns the authoritative parent and subagent indicator projection for the Web UI: a snapshot for initial load and reconnect, followed by live deltas.
  • The existing connected-agent list API remains compatible for tmux and router-managed agents.
  • Existing consumers can use the router message API the same way for tmux and router-managed agents.
  • Router-managed Pi agents receive mailbox messages directly in the router-managed RPC path.
  • Every agent has a send-message tool. The router-managed tool is registered by the thin extension.
  • The tool feeds sends into router behavior equivalent to an API call.
  • The tool does not accept a from parameter. The router derives the sender from the agent's registered identity.
  • When a thin-extension tool runs, it sends a structured JSON control request to the router. The router interprets the request and calls the matching existing or new internal handler.
  • Control traffic is a dedicated protocol, not ordinary mailbox or conversational traffic. Its envelope has an explicit control discriminator or customType, a request identifier, an allowed operation, and a payload. The router validates the envelope, derives the sender from the router-managed process, and dispatches only allowed operations.
  • Every thin-extension tool is asynchronous or fire-and-forget. It emits its control request and returns without waiting for router handling. Fire-and-forget calls receive no later response. An asynchronous operation may later receive a correlated result or error as a new control message from the router. Dynamic registration does not change these control-request semantics or amend an already returned Pi tool result.
  • Research must prove the router-to-agent delivery path for later control messages and define the immediate tool return honestly. A failed operation or failed later delivery must be visible in complete history.
  • Fire-and-forget calls may use custom session messages with customType and details.
  • The router does not use Origin or host origin as authorization for the managed HTTP or WebSocket surface. Requests may come from any host or origin that can reach the router, and non-browser clients without Origin remain supported. This does not change bind, listen, exposure, Tailscale, or public-network configuration.
  • Browser-session authentication, request correlation, CSRF protection for cookie-based state-changing requests, WebSocket session authorization, and secret redaction establish authority. Origin does not. This adds no new authentication framework.
  • The supervisor is an ordinary worker for now. No lifecycle behavior depends on the worker name supervisor.
02

What must be available in the Web UI

Settled
  • The RPC path has no console or terminal view.
  • The Web UI must cover the visibility and controls Wolfgang needs for the RPC path.
  • The Web UI has launch, restart, and terminate controls. Router APIs are also available.
  • The launch form accepts a worker name, a path, a model, and an optional initial instruction.
  • The launch path is always a working directory. The picker selects folders, and the path can also be entered as plain text.
  • The model is selectable for each launch.
  • The optional initial-instruction input can insert or paste prompt templates, like the worker input in today's Web UI.
  • The Web UI has global router settings.
  • The router settings dialog lets Wolfgang select the default worker model from the models available to Pi.
  • If no default model is configured, the router uses GPT-5.6 Terra.
  • If the configured default model becomes unavailable, the router falls back to GPT-5.6 Terra.
  • Restarting an agent resumes the same Pi session.
  • The Web UI must show the actual state of each agent. A router-managed parent's active and compacting indicators come from structured Pi RPC state or events, never from terminal text or status inference.
  • The Web UI shows a visible source indicator for each agent: tmux or router-managed. This is the only user-visible source distinction.
  • The Web UI lets the user view subagents nested under or associated with their router-managed parent. Each entry shows a stable task identity, description or name, model when known, structured lifecycle state, and elapsed time while active or finished timing when terminal.
  • The subagent view shows running, completed, failed, or stopped only when structured evidence supports that state. It preserves a more precise structured state when available and does not infer a lifecycle state from missing events or terminal text.
  • The router keys a child association by parent worker identity, parent Pi session and process fencing, and subagent task ID. Terminal records also preserve their parent entry identity and timing so a resumed task ID cannot attach an old run to a new incarnation.
  • After a router restart or parent-session switch, the router reconstructs current active subagent state before publishing it. It does not rely only on previously observed live deltas.
  • Parent compaction appears as transient compacting activity from structured Pi compaction start, end, error, or reconciled state. The indicator clears deterministically after completion, failure, disconnect, or restart reconciliation.
  • Child compaction appears in the nested view when structured child telemetry supplies it. It uses structured forwarding or an authoritative snapshot, never terminal-text parsing.
  • At minimum, each agent has a simple state view: pretty-printed JSON in a code-viewer popup.
  • Errors appear in the complete history. They do not need a separate persistent acknowledged or cleared state.
  • The Web UI has two separate histories. Wolfgang can switch between a quiet view and a complete view.
  • The quiet view shows only messages an agent explicitly sends with the new send-message tool to Wolfgang's router-wide canonical_quiet_recipient_id. Protocol traffic stays out of this view. A tool call appears here only when its actual purpose is to send that message; the protocol traffic and resulting message remain distinct.
  • canonical_quiet_recipient_id is an explicit operator setting for Wolfgang, persisted router-wide and required before managed mode starts. It uses exact validated identifier equality, never a display name, browser-local owner, or inferred history alias. It may change only through operator configuration and router restart; retained entries preserve their write-time eligibility.
  • The complete view shows all agent activity, including tool invocations, control requests and responses, parent and structured child compactions, reminders arriving, messages arriving from other agents, and other activity. Runtime indicators and their lifecycle changes do not enter quiet history.
  • The quiet history retains up to N messages. N is the current router per-conversation limit and must be found through research.
  • The complete history retains up to 200 activity entries total, including tool calls, compactions, reminders, errors, messages, and other activity.
  • The histories stay separate. Complete-history activity does not wipe out or evict messages sent directly to Wolfgang.
03

Provider authentication

Confirmed defaults
  • Router-managed Pi agents must support provider authentication.
  • The minimum providers are ChatGPT, Google, and Cursor through pi-cursor-sdk.
  • The Web UI is the required provider login and logout surface. It starts and coordinates Pi's supported secure authentication interaction. No terminal is required.
  • The Web UI shows non-secret provider authentication status only. Credentials remain in Pi's protected authentication store. Router state never stores credential material, browser state, or raw authentication data.
  • One router-wide provider and account context is shared by every router-managed agent. The product has no per-agent provider-account selection or credential store.
  • Launch and router-directed model selection use only models available from that shared authenticated context.
  • A successful login or logout changes the shared context for every router-managed agent's future operations. An agent may finish its current turn. Before it receives further work, the router restarts it on the same Pi session so it loads the changed shared context.
04

Implementation validation

Required validation

These checks establish technical capability and evidence. They validate implementation choices. They do not leave product behavior undecided.

What is the router launch API?

Verify its request and response shape, validation, the direct Pi connection it starts, and its lifecycle mechanics. Do not add request fields until the API is known.

Can RPC report structured parent state and compaction?

Verify the JSON state and event fields for parent active and compacting indicators, including compaction start, end, error, disconnect, and reconciliation behavior.

What is N?

Find the current router per-conversation message limit. Also verify its expiration and retention behavior.

Which crash-loop policy meets the bounded-recovery requirement?

Validate a deterministic restart limit, window, backoff, healthy-reset rule, and manual-recovery behavior from evidence.

How does the router deliver later control messages?

Every thin tool returns after emitting its control request. It does not wait for a router response. Custom session messages are one-way, so research must prove how the router delivers a later control message to the extension for an asynchronous result or error. Define the immediate return, failed delivery, duplicate, and correlation behavior from the experiment.

How does the router install dynamic tools?

Independent validation proves late registration and next-turn schema exposure in Pi. It does not prove the production router executor, generic dynamic closure, same-call tool result, or router end-to-end result delivery. Validate the hashed runtime-generation manifest, raw-input/schema bounds before coercion, atomic registration, collision and immutable-name rules, first-turn gate, separately accepted add-only updates, and same-session restart for changed definitions. Do not claim safe in-place removal or replacement.

How are thin tools, messages, and helpers handled?

Verify that the thin extension registers every required router-backed tool, that control requests cannot enter ordinary mailbox handling, and how mailbox messages reach RPC Pi agents. Verify the structured subagent lifecycle and compaction telemetry available to the router. Raw parent RPC does not itself expose child streams or child-compaction events.

How do tmux and RPC stay compatible?

Verify the current tmux connection protocol, the paths that post messages or indicators into an agent, and what must stay unchanged for tmux support.

What state belongs in the router?

Keep state in the router wherever possible. Validate the authoritative parent and subagent snapshot, live-delta, composite-identity, and restart/session-switch reconstruction rules, including how generated session IDs map to processes, resume, context reset, and router recovery.

How does the router obtain current active subagents?

Current raw Pi has no direct child-list RPC. Validate the exact snapshot source for initial load, reconnect, router restart, and parent-session switch. The smallest required addition is structured child lifecycle telemetry with current compacting state in the router's authoritative snapshot. Do not substitute terminal-text parsing.

How does the router get Pi's available-model list?

Document the current extension-backed model-list path for tmux agents and the router-managed path. Keep the tmux path unchanged.

How do the histories work underneath?

Investigate event collection, separate storage, and retention so the quiet and complete views remain independent.

Which supported Pi interactions serve the required providers?

Validate the ChatGPT, Google, and Cursor paths through pi-cursor-sdk. Additional Pi providers remain optional.

What core-RPC authentication limit must the Web UI handle?

Validate that core RPC has no login, logout, or provider-status operation. The Web UI must coordinate a supported Pi authentication interaction without exposing credentials.

Which supported Pi integration implements Web UI authentication?

Validate the secure interaction path and its browser or device-code handoff. Keep the thin extension's dedicated control protocol unchanged.

Does the Web UI preserve Pi's credential boundary?

Verify that the supported Pi authentication flow keeps credentials in Pi's protected store and exposes only non-secret status to the router and Web UI.

How does the shared authenticated context affect model selection?

Verify that router settings and launch selection use the shared context's available models, and that a completed login or logout refreshes each router-managed agent before its next turn.

05

Settled product defaults

Confirmed
  • Restart All applies only to router-managed RPC agents.
  • Tmux agents remain visible and can exchange messages with router-managed agents. They are excluded from Restart All because the router does not own or reliably restart their processes.
  • Tmux deprecation and removal are future direction. This project adds no removal date, migration feature, or tmux-removal work unless another confirmed requirement already requires it.
  • A router-managed restart still resumes the agent's same Pi session.
06

Observable success criteria

Required checks
  • Every router capability or tool required by the parity inventory is registered by the thin extension. An inventory omission cannot create a parity gap.
  • A control request never enters ordinary mailbox or conversational handling.
  • A malformed envelope or unknown operation is rejected without invoking an internal handler. The rejection appears in complete history.
  • Valid authenticated managed HTTP requests from two unrelated HTTP(S) origins both succeed, as does a valid non-browser request without Origin. Missing or invalid browser session, WebSocket session ticket, or CSRF proof fails independently of Origin before an effect or upgrade.
  • A caller cannot spoof sender identity. The router uses the identity bound to the router-managed process.
  • Each accepted request invokes its matching handler once. A duplicate request does not invoke the handler again.
  • Every thin-extension tool returns after emitting its control request. It never waits synchronously for router execution, a result, or an error.
  • An asynchronous operation's later result or error is delivered as a new control message and correlates to its request identifier. Fire-and-forget operations produce no later response.
  • Operation failures and failed later-control delivery are visible in complete history.
  • Control requests, later results or errors, and tool activity appear in complete history. They do not enter quiet history.
  • Only a resulting message from the new send-message tool to Wolfgang's canonical_quiet_recipient_id enters quiet history. That message remains separate from its control traffic.
  • Managed mode does not start without canonical_quiet_recipient_id. A configuration replacement after router restart affects future messages only and does not reclassify retained rows.
  • A user completes login and logout for each required provider from the Web UI. Pi completes the supported secure interaction without a terminal, and the Web UI displays only non-secret status.
  • Credential inspection confirms that Pi's protected authentication store holds credentials and router state contains only non-secret provider/account status and selected-model metadata.
  • After a shared-context login or logout, an idle router-managed agent restarts on its same Pi session before its next turn. A working agent completes its current turn, then restarts before further work. The restarted agents expose only models from the changed shared context.
  • Restart All restarts every router-managed agent and no tmux agent. Tmux agents remain listed and message-compatible, and their processes receive no restart request.
  • Drive parent work and compaction start, end, and error signals. The live UI and complete history show the structured active and transient compacting states. They never infer either state from terminal text, and compaction clears after completion, failure, disconnect, or restart reconciliation.
  • Start subagents with known task identities, descriptions, models, and lifecycle outcomes. The router-managed parent shows each nested child with its supported lifecycle state and elapsed or finished timing. Exact structured states remain distinct when telemetry provides them.
  • Load and reconnect the Web UI while children are active, then restart the router and switch the parent session. Each view begins with an authoritative snapshot and receives live deltas afterward. Active children reconstruct without relying only on old deltas.
  • Deliver a stale child event after a parent process, session, or task run changes. The composite parent fencing, task identity, parent entry identity, and timing prevent it from attaching to the current child.
  • Trigger child compaction through structured telemetry. The nested child view and complete history show it. If current Pi does not provide that telemetry, the required structured extension event and snapshot field are added before this criterion can pass. Quiet history remains unchanged.
  • Start a router-managed process with the complete 16-tool manifest. The reserved command validates the canonical hash and current runtime generation, then registers every tool atomically before the first model turn. The router marks the agent ready only after the accepted manifest result. The first model request sees the exact registered schemas.
  • Exercise independently verified Pi scope: install one late tool through the reserved extension command and capture the next model request. It contains that exact name, description, and schema. Treat this as Pi registration evidence only, not proof of router execution or result delivery.
  • Deliver malformed JSON; a manifest above the raw byte bound; coercive values; $ref, composition, unsupported types or keywords; an array whose maxItems bound would fail; missing finite bounds; reversed ranges; unsafe property names; and excessive depth. Every case rejects before coercion or registration, exposes no partial tools, and records the failure in complete history.
  • Deliver duplicate names in one manifest, a repeated installed manifest name, a real built-in collision, an existing-extension collision, unsupported protocol, hash mismatch, stale runtime generation, and a partially invalid multi-tool manifest. Every case rejects atomically. A startup failure stays not ready; a later update preserves its current tool set.
  • Deliver a validated later manifest containing one previously unused tool name through the separately accepted add-only update path, with no more than 32 definitions in the target. The running process exposes that new immutable name without an extension code update. Existing manifest tools keep their original definitions and control-request behavior. A target above 32 definitions rejects without changing the installed tool set.
  • Deliver a changed definition for an existing tool name. The running process rejects the in-place change. Assign <capability_id>__<definition_sha256>, restart on the same Pi session, deliver the new full manifest before work resumes, and verify the new definition. Context reset does not occur.
  • Start a fake-router operation through a dynamically registered tool. A call with an unexpected property rejects before any request or side effect; a valid call makes the generic closure emit one dedicated request with the exact tool name, Pi tool-call identifier, validated arguments, manifest hash, runtime generation, and allowlisted operation. It returns its bounded asynchronous result before a delayed completion. Timeout, cancellation, error, replay, and stale-generation cases do not execute an unallowlisted operation or amend the original tool result.
  • Issue a session switch, reload, resume, fork, process restart, and reconnect. Each creates or reconnects a fresh extension runtime generation, replays the exact current manifest before the next model request, and fences the old generation.
  • Add a router tool within the selected 32-definition limit by changing only router manifest and handler data. The fixed extension code remains unchanged. The new tool registers through the validated manifest and invokes the existing asynchronous or fire-and-forget control path. Full router end-to-end dispatch and later-result delivery remain acceptance work.
Confirmed direction and technical research are intentionally separate.
