The router starts and supervises Pi directly, keeps durable product state, exposes the required controls in the existing Web UI, and leaves the current tmux path intact. Router-managed Pi has no terminal surface. A fixed thin extension carries a mandatory startup manifest and structured control traffic; it does not own product behavior.

01

Status and scope

Implementation-ready direction

This document resolves lifecycle, persistence, protocol, provider, Web UI, history, child telemetry, race, failure, and cleanup behavior. The implementation may change a named mechanism only when direct evidence shows that mechanism cannot meet an acceptance criterion. Product behavior and scope do not reopen.

Runtime evidence boundary

Installed Pi 0.85.0 has proven late registerTool() and next-request visibility. The manifest fixture did not prove the router executor, generic tool closure, strict uncoerced input, later add-only installation, or late result delivery. Those are acceptance work, not facts already established. The companion research records evidence and earlier open questions; where it still says a decision is open, this normative specification supplies the selected decision.

In scope

  • Router-owned Pi RPC processes, sessions, restart recovery, direct mailbox delivery, state, and histories.
  • The existing React router UI: launch, state, lifecycle actions, models, provider auth, nested children, and two history views.
  • One fixed Mecha thin extension, plus the existing pi-subagents extension with the smallest structured lifecycle additions.
  • All 16 required baseline capabilities under their exact revision-one names, plus the bounded add-only manifest path required to add later router tools without changing the fixed extension.

Explicitly out of scope

  • No tmux deprecation, removal, migration milestone, or router-created tmux worker.
  • No terminal, console, shell, or arbitrary process interface for router-managed agents.
  • No generic RPC fork, generalized event bus, durable workflow engine, sidecar daemon, or second process supervisor.
  • No per-agent credential account, extra provider promise, tool marketplace, arbitrary manifest code, or unrelated UI redesign.
01A

Active Phase 2 simplified worker contract

Authority and preserved history

This is the normative contract for the active Phase 2 worker launch work and the current restart slice. Router worker control is locally unauthenticated: any page or process that can reach the router may operate workers, with no application-layer caller identity or authorization step. It supersedes conflicting Phase 2/restart-slice browser-session, cookie, CSRF, ticket, Origin/CORS-response, fixed/pinned dependency, and fixed/pinned launcher-input statements elsewhere in this document and in RPC_IMPLEMENTATION_PLAN.html. The actual replacement ledger owns active-turn settlement as its first execution gate after the closed preparation transition; no standalone settlement slice is a prerequisite. Those statements remain visible as historical design evidence, not active acceptance requirements. This rebaseline does not change Phase 1’s fixed thin-extension and pi-subagents compatibility contract, current legacy tmux routes, bind/exposure rules, direct-argv/no-shell rule, containment, process/session fencing, strict request parsing, limits, retention, redaction, or other unrelated security behavior.

Direct worker HTTP

The active managed routes are direct worker control routes, not browser-session routes. Any page or process that can reach the router can invoke them. POST /v1/managed-agents, the current single-agent projection, and the future restart route accept their documented closed request bodies. Every mutation requires a canonical UUID X-Request-ID; responses retain the matching request and operation ID. The request ID is an idempotency/correctness key, not an authority proof. No managed route requires or issues a UI-session cookie, CSRF token, ticket, browser bootstrap, or other caller credential. POST /v1/ui-session is removed from active Phase 2. The existing /v1/agents contract remains unchanged and does not receive session-gated managed rows in this slice.

The router does not read, validate, reject, reflect, or authorize by Origin for an active managed route. It has no managed CORS, credential, Vary: Origin, or preflight response requirement. Existing router-wide generic CORS behavior may remain intact as a legacy behavior, but it is neither managed-route authority nor an acceptance target.

Worker-wide idempotency without a session

The durable key is (method, X-Request-ID) in one router-managed-worker scope. An exact canonical path/body replay returns the retained response; a changed path or body returns 409 IDEMPOTENCY_CONFLICT. Terminal rows expire after 24 hours and nonterminal rows remain until terminal. There is no authorization or caller identity step before lookup. Router bind, Tailscale, and exposure configuration remain the separate reachability controls and are unchanged by this application contract.

Applied migration 022_managed_rpc.sql is preserved. Until a deliberately separate schema cleanup, its session_identity_hash column is only a storage-compatibility operation-scope column. New operations write the non-secret constant router-managed-worker-v1; it never comes from a session, cookie, CSRF value, header, Origin, or caller. Public manager/store APIs must not expose or require that legacy column. The uncommitted 023_managed_restart.sql remains a forward restart-transition migration and needs no session-related rewrite.

Unpinned launch boundary

Enabled worker mode requires a usable Pi executable, managed home, session root contained by that home, strict generated manifest, mecha-rpc and pi-subagents entry files, allowed working-directory roots, canonical quiet recipient, and bounded limits. The router validates resolved path type and containment, manifest shape, direct argv, sanitized environment, live process identity, and readiness. It does not require an exact Pi version, file/tree hash, lockfile/package identity, generated pin, helper, Cursor extension/package, or built UI.

Phase 2 supplies the static worker catalog openai-codex/gpt-5.6-terra through CatalogFromModels. An explicit selection still has to be in that catalog. Provider login, discovery, helper processes, and Cursor support are future work, not a Phase 2 startup dependency.

03

Minimal architecture and ownership

Router process

Extends the current Go router. It owns SQLite records, one direct child pi --mode rpc process per running managed agent, serial stdin writes, stdout event parsing, stderr capture, lifecycle policy, messages, tool handlers, auth coordination, and browser publication.

Fixed thin extension

Receives the mandatory manifest, registers data-defined tools with one code-defined closure, captures strict raw arguments, emits hidden control messages, accepts fenced result/mail/policy commands, and applies only Pi-local mechanical policy. It opens no router socket.

Existing subagent extension

@gotgenes/pi-subagents remains the child runtime owner. Its current snapshot-only result and owner-session behavior are retained. The wolfgangmeyers/pi-packages fork’s main branch is its source of record. Phase 1 runs the package’s existing checks and build:types, then gives stock Pi the package-declared ./src/index.ts entry as a fixed extension path. The structured lifecycle snapshot, delta, compaction, child-control bridge, and owner-bound child inline-extension registration named here are minimal prescribed project changes to that package; they are not claimed as installed Pi RPC APIs or current package behavior.

Existing Web UI

The React router manager merges the existing connected-agent projection with the managed registry. It renders source, state, controls, provider flows, histories, and expandable child rows. It consumes authoritative snapshots and fenced deltas; it never parses terminal or transcript text for activity.

One-shot auth helper

A new project-owned Node entry point performs one structured auth/model operation and exits. Its design is patterned after the inspected Wolfgang-fork ModelRuntime source and uses the pinned provider/auth libraries, but it is not a stock Pi RPC command and the fork is not a runtime dependency. This narrow helper exists because installed Pi RPC has no login, logout, or credential-mutation command; it is not a service or credential store.

Only three transport boundaries
  1. Router ↔ managed Pi: stock newline-delimited Pi RPC over the child's stdin/stdout. Application commands and hidden custom messages carry the reserved Mecha protocol inside supported Pi behavior.
  2. Browser ↔ router: the HTTP routes and existing live WebSocket described below.
  3. Tmux Pi ↔ router: the existing Mailbox V2 WebSocket and HTTP behavior, unchanged. Router-managed Pi never connects through this boundary.

There is no generic controller protocol, extra local daemon, new message broker, or Pi core fork.

Current Phase 2 restart-slice contract

Rebaseline: reservation has the direct worker idempotency scope defined in Active Phase 2 simplified worker contract; it does not receive, validate, or persist a UI session identity. The rest of this slice remains unchanged.

This slice adds reservation and preparation only. Crash-loop execution, router-restart execution, policy projection, authoritative child snapshots, public prompt delivery, browser UI, and provider auth remain future work.

  • Eligibility: a restart reservation requires desired_state=running, lifecycle_state=running, accepting_prompts=true, slot_held=true, and activity_state of active or idle. It also requires one exact live router-owned process/RPC binding whose session ID, session epoch, process incarnation, runtime generation, PID/start marker, and process-group leadership match the durable fences. No restart transition may already exist for the agent.
  • Atomic reservation: store.ReserveManagedRestart uses one immediate transaction to create the single bounded restart transition and set accepting_prompts=false. managed.Manager runs that transaction through the same per-agent serializer used for admission.
  • Preparation: after reservation, get_state runs under one five-second deadline before a stop signal, replacement start, or prompt delivery. A deadline expiry or any state-read error runs the rollback transaction. It deletes the transition, restores the pre-reservation desired/lifecycle/activity/prompt/slot values, and records exactly {code:"RESTART_PREPARATION_FAILED",message:"restart preparation failed"} in the durable last error. The raw timeout or state-read text is not durable.
  • Internal prompt-admission seam: managed.Manager.AdmitPrompt(ctx, agentID, message) is internal Go code. It holds the same per-agent serializer, reads the durable ready and accepting state plus the exact live binding, then calls that binding's RPC.Prompt. Any failed admission returns the typed AGENT_NOT_READY result without a prompt call or queue. This slice adds no HTTP route, browser state, manifest command, or P3 surface.
  • Required tests: TestReserveManagedRestartAtomicallyDisablesPromptAdmission admits one fake prompt before reservation, then proves the next admission returns AGENT_NOT_READY and the RPC prompt count does not increase. TestRestartPreparationFailurePersistsExactDurableError covers a five-second get_state timeout and a state-read error; both assert the exact durable code and message above. TestReserveManagedRestartRejectsIneligibleRowsWithoutEffects covers every failed eligibility condition and asserts no operation or transition, no agent-row or projection-version mutation, no slot mutation, and zero process/RPC/async calls.
Recorded actual restart replacement entry and 17-path ledger

The closed 023 reservation/preparation slice remains unchanged. It ends when its owner commits prepared. The complete 024 five-gate readiness source is the prior dependency. This replacement ledger owns active-turn settlement as execution gate 1. There is no standalone settlement slice and no idle-only replacement path.

For an active reservation, ExecutePreparedRestart persists settling, waits for the exact old binding's structured agent_settled event, and persists that same-binding result before it can record stopping. A settlement failure keeps the transition at settling, the old group live, prompt admission closed, the slot held, desired state running, and the operation pending.

Migration 025 and ownership

Migration 025 rebuilds only managed_restart_transitions. It retains the old fence and target runtime generation, adds turn_settled_at plus the target session, epoch, PID, start marker, incarnation, manifest revision, and manifest hash, and permits only reserved, prepared, settling, stopping, stopped, and starting. settling and turn_settled_at are active-reservation state only. Active stopping, stopped, and starting require turn_settled_at; idle transitions do not enter settling. The target fence is all null before starting, complete at starting, and cleared if target cleanup returns to stopped.

rpc.go owns structured settlement evidence. The store owns MarkManagedRestartSettling, MarkManagedRestartTurnSettled, MarkManagedRestartStopping, and the remaining stage/full-fence transactions. The supervisor owns the persistent agentLane, immutable runtimeBinding, and ordering: write settling, call the RPC settler, write its exact same-binding result, then stop. The durable old-fence settlement write permits that stop even if its settlement handler has begun an old continuation. Store writes are immediate transactions. A stale write is a no-op with no projection bump.

Safety acceptance

  1. The diff contains only these 17 replacement paths. Migration 025 preserves 023/024 data and indexes. The store_test.go change solely advances the startup-clock expected count from 20 to 21.
  2. Direct restart has exact request-ID, replay, conflict, private-field, and Cache-Control: no-store behavior. It is locally unauthenticated and reads no browser credential or Origin.
  3. Both active and idle reservations use the closed active-or-idle reservation seam. Active work never stops before durable structured same-binding settlement. agent_settled is a drain boundary, not idle proof.
  4. One old group is proved absent before one target starts. The target keeps session, epoch, model, cwd, manifest, direct argv, and sanitized environment with a new process incarnation.
  5. Prompt admission remains closed in every nonterminal stage. An old continuation started from a settlement handler never reaches the target by forwarding, replay, resume, or re-admission. The initial instruction is never sent again.
  6. Failure, cleanup, close, stale callback, and recovery paths retain their safe durable state. They do not start a second target or create another projection bump.
  7. Only the target's completed five-gate readiness transaction reopens admission. It consumes the 024 source predicate under the target fence. The target has no model turn before that readiness and newly accepted input.
  8. No direct mail, controls, policy or child implementation, UI, browser session, reset, terminate, Restart All, crash policy, general recovery, P3, P4, or Robot Review belongs to this documentation amendment or replacement ledger.

Lifecycle and activity values

lifecycle_state: starting, running, restarting, resetting, terminating, failed.

activity_state: starting, waiting, active, idle, compacting, stopped, failed.

compacting overrides active/idle. waiting means a router-accepted prompt is queued but Pi has not emitted agent_start. No value comes from prose.

Readiness gate

  1. Pi RPC answers get_state; session identity matches the intended record.
  2. Reserved command collision preflight passes.
  3. The mandatory full desired manifest is accepted atomically for this runtime generation.
  4. get_active_tools contains exactly the accepted full manifest's Pi-visible names: one current definition for each of the 16 required baseline capabilities plus any accepted supplemental capabilities.
  5. Policy projection and the prescribed authoritative child snapshot operation complete.

Canonical identity and immutable naming
  • The router sorts desired_manifest.tools by UTF-8 byte order of capability_id. manifest_sha256 is lowercase SHA-256 of the RFC 8785 canonical UTF-8 bytes of exactly desired_manifest; envelopes, delivery IDs, runtime/session fences, and policy projections are excluded.   • The command has exactly one unpadded base64url argument. Reject more than 174,763 ASCII characters before decode; decode at most 131,072 bytes before UTF-8 validation; use a duplicate-key-detecting JSON parser before object construction. Reject trailing bytes, invalid UTF-8, malformed JSON, non-finite/unsafe numbers, forbidden keys (__proto__, prototype, constructor), and any unlisted envelope/tool/schema field.

Security, bounds, and failure containment

Process boundary

  • Router configuration fixes the Pi executable, managed session root, thin extension, subagent extension, auth helper, allowed cwd roots, and maximum 32 running managed agents.
  • User input never selects executable, flags, environment names, extension paths, session path, or process ID. Use direct argv, never a shell.
  • Resolve cwd and session paths with realpath; require containment before launch or delete. Symlink escape fails.
  • Persist PID plus OS start marker and random incarnation. Signal a process group only when all match.

Protocol bounds

  • Pi stdout line: 1 MiB; stderr logs: five 1 MiB rotated files per agent; invalid/oversized output fails that process.
  • Control raw arguments: 32 KiB, depth 8, 2,048 nodes, 256 properties/object, 256 items/array, 8 KiB/string.
  • Control result decoded: 64 KiB; model-visible content and stored detail: 16 KiB each, with current secret redaction.
  • At most 64 nonterminal controls per agent and 512 router-wide. Handler deadline is 30 seconds; model turns and deferred compaction are not handler calls.

Direct local authority boundary

  • This is a new, managed-surface-only protocol. Any page or process that can reach the router may use managed HTTP and UI-live. This application-layer rule does not change bind, listen, exposure, Tailscale, or public-network configuration. Existing agent WebSocket and legacy route contracts remain unchanged.
  • The router does not read, validate, reject, reflect, or authorize by Origin, Host, or a derived origin value for managed HTTP or UI-live. Requests from unrelated origins and non-browser clients without Origin have the same managed result when otherwise valid.
  • Managed routes issue and accept no session, cookie, CSRF value, bearer value, ticket, or browser bootstrap value. Mutations require closed JSON and X-Request-ID for worker-wide idempotency. It is not authority.
  • /v1/ui-live has no query parameters or browser credential. Its first frame is the current full snapshot. A duplicate, regression, or gap makes the client discard deltas and reconnect for a new snapshot.
  • The hub may keep a bounded internal connection handle for cleanup. It is not a caller identity, session, or permission grant. Live frames contain no provider secret, raw process output, credential path, or browser credential.
  • Destructive reset, terminate, provider logout, and Restart All require a confirmation naming the effect. Disable controls while their mutation is pending. Auth prompt responses are one-use and operation/prompt-correlated, expire after ten minutes, and are never echoed.

Failure containment

  • Malformed frames, stale fences, unknown operations, and invalid schemas create bounded complete-history errors and no side effect.
  • Subprocess stderr and external adapter output use the existing structural credential redaction before logging/history.
  • No control protocol record enters ordinary mailbox dispatch. No ordinary message is interpreted as control.
Browser rendering and response headers

All model, agent, path, history, provider, error, and JSON-state values render as React text nodes; no managed surface uses dangerouslySetInnerHTML, raw HTML injection, executable links, or secret-bearing DOM attributes. The state popup uses text content inside <pre>. Provider URLs are parsed and allow only https: before becoming links.

The router-served UI sends Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self' ws: wss:; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self', X-Content-Type-Options: nosniff, and Referrer-Policy: no-referrer. JSON responses use application/json and Cache-Control: no-store. These controls apply only to the router UI/new managed surface; this project does not create a generalized user-auth system.

The 32-process cap, protocol byte limits, 30-second handler deadline, five-second graceful/TERM stages, and log rotation sizes are selected bounded local operating policy and must pass boundary tests. They are not represented as values proven by upstream Pi research.
