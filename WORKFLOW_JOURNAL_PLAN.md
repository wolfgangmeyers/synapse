# Workflow run lifecycle journal plan

## Outcome and scope

Provide a durable, atomic journal for all workflow runs, including background and scheduled runs. People can ask the agent to add notes, inspect timelines and duration distributions, browse retained runs, and delete completed runs. The system prompts for a human-facing journal entry at every transition and exit; reasons remain distinct and optional. Agent deletion, including background cleanup, removes that agent’s journals. Preserve existing workflow authorization, goals, snooze and return behavior. This document is planning only.

## Current architecture and UX

- `router-proxy/internal/store/workflow_transition_authorization.go` and `workflow_predecessor.go` implement authorization and binding-generation fences. `managed/embedded_workflow_transition.go` mutates binding and separately handles reminders, monitors, history and guidance. Existing history is not an atomic journal.
- Activation and administrative mutations also enter through managed tools, `transport/managed_http.go`, the background runner and schedules. Agent, state and workflow deletion and background cleanup affect bindings. Inventory all writers; journal at shared transactional store boundaries, not only in the transition tool.
- `docs/specs/workflow-implicit-return.spec.md` preserves predecessor and lifecycle behavior; `workflow-implicit-goals.spec.md` governs goals, snooze and execution-evidence retention. Its evidence retention policy is not a run-journal policy. Background workers become eligible for termination at 24 hours from creation, with startup/minutely sweeps and possible delays (`background-worker-cleanup.spec.md`, `background_expiry.go`). When cleanup deletes the agent, its journals disappear too, just like explicit agent deletion: background journals may therefore be short-lived, not retained for 90 days.
- `ConversationHeader.tsx` already exposes an agent-scoped progress-history action, workflow controls and a clickable `workflow-state-badge` whose `onOpenWorkflow` manages workflows. `App.tsx` owns the progress modal selection. `ProgressHistoryModal.tsx` provides the relevant chart, expandable entries and loading/error/empty patterns. `WorkflowsPage.tsx` uses `DialogShell` with `message-dialog delete-confirm-dialog`, Cancel and `btn-danger` for workflow deletion.

## Contract and design

1. **Runs and events.** Allocate a unique run ID on each successful activation, including same-workflow reactivation, scheduled and background launches. Snapshot agent, workflow and state IDs and display names, initial state and server start time. Append ordered events for state entries, explicit and implicit returns, exits, notes and administrative termination/replacement. Cross-workflow edges remain the same run with both definition snapshots; self-transitions are distinct visits. Identify each visited state by the pair (workflow ID, state ID), not name or state ID alone; snapshot both names. A visit has its own stable identity and a per-run monotonic sequence defines order. Aggregate revisits only for the same workflow/state pair, never merge identically named states from different workflows. Rejected or stale mutations create no lifecycle event.
2. **Atomicity.** In one SQLite transaction validate binding generation and authorization, mutate binding/predecessor and run status, and append the lifecycle event. Apply this to activation, transition, exit, reassignment, deactivation and relevant deletion paths. Journal failure rolls back binding mutation. Concurrent contenders have one winner. Define stable operation identity and retry semantics to prevent duplicate events after a committed retry. Notifications, reminders and monitors remain post-commit effects, not part of the atomicity claim; missed WebSocket updates recover by REST refresh.
3. **Entries, reasons and prompts.** Every successful agent transition and exit MUST prompt the agent to write a concise human-facing entry. Use the existing synchronous transition-tool result guidance (`embedded_workflow_transition.go`) for both paths; preserve existing guidance and do not add a durable delivery/retry protocol or promise delivery across crashes. The prompt asks for the outcome, important decisions, obstacles and next steps when relevant; use plain language, omit jargon and routine noise, and never fabricate missing facts. Include stable run and event identity in the response and allow the resulting entry to target that event even after exit or a subsequent transition, with agent ownership checks; do not infer its target from the current binding. If the target event or run has since been pruned or deleted, return a clear not-found error rather than attach it elsewhere. Do not claim an entry exists until written or block the transition on composition. Keep optional bounded plain-text `reason` on transition/exit and applicable administrative/API schemas distinct from the prompted entry: blank means absent, oversize is rejected, and neither is fabricated or silently truncated. Make a discoverable `workflow_journal_note` tool available for the agent to proactively record useful bounded human-facing notes, as well as when a human asks; this is how people add notes, not a separate UI editor. Record source and timestamp; specify no-active-run errors for ordinary notes, authorization, tool admission and rejection of unauthorized writes. Ordinary conversation is not automatically a note.
4. **Read API and analytics.** Add paginated stable list and detail/timeline endpoints with agent, workflow and status filters. For a selected run, chart the distribution of time spent in each state, aggregating all visits to the same workflow/state identity, including revisits, while keeping distinct workflows separate even when names match. Derive durations from lifecycle timestamps, define how an active run's current visit is measured and how clock rollback is handled, and identify incomplete synthetic legacy history without inventing earlier durations. Do not substitute a distribution of completed-run durations. Expose retention and filter scope.
5. **Concrete UX.** Add a distinct, accessible **Workflow journal** action to `ConversationHeader.tsx`, scoped to the selected managed agent and available even when no workflow is currently active, so its retained runs remain discoverable. Wire selection/modal state in `App.tsx` following the existing progress-history path. Do not repurpose or break the clickable workflow state badge or its management action. Build an agent-scoped journal modal modeled on `ProgressHistoryModal`: select a run to see its per-state time distribution and a sci-fi styled vertical scrollable timeline of chronological state visits with each visit’s duration visible without expansion; expand visits for reasons, entries and notes, plus loading, error and empty states. Use the existing dark glass design, blue workflow accents and 24px `.icon-btn-round` icon actions. Make controls labeled and keyboard-accessible, handle narrow screens and safely render text. Include all retained runs for that agent, not only its current workflow. Do not provide orphan-history routes or access to journals for deleted agents.
6. **Manual cleanup.** Offer Delete only for terminal runs. Use the existing `DialogShell` workflow-delete confirmation pattern, identifying the run and warning that its timeline and notes are permanently removed; Cancel does nothing, pending disables repeat submission, and errors remain visible. Add a matching DELETE endpoint. In one transaction recheck terminal status and delete only that run and its events ; explicitly handle not-found, concurrent completion, double delete and retention races. Refresh the modal and selected-run chart after success. Manual run deletion must not delete an active run, another run, an agent, a definition or execution evidence. Agent deletion is a separate lifecycle cleanup that removes all of that agent's runs, including active ones, and their associated records.
7. **Restart and migration.** Persist active run identity with binding authority. Cold restart continues the same run without a duplicate start. Migrate existing active bindings once to marked synthetic/incomplete runs at migration time and current state; don't infer earlier events, reasons or durations. Historical unjournaled runs cannot be reconstructed; disclose that. Migration and startup must be idempotent and transactionally safe.
8. **Administrative lifecycle.** Inventory actual successful paths for exit, deactivation, reassignment including same workflow, state replacement, state/workflow deletion, agent deletion, failed background startup and background expiry. Specify journal effects for each observed binding mutation, preserving existing behavior rather than assuming every administrative operation closes a run: close it with an administrative outcome only when that path actually ends or replaces its binding; start another only on actual activation. Record nonterminal changes if the binding continues. Failed and rejected operations create no phantom lifecycle events. Agent deletion removes all of its journals and associated records as part of deletion, including background expiry or other background cleanup; no orphan journal is retained or exposed. Preserve snapshots for retained runs when workflow or state definitions are deleted. Preserve existing authorization and cleanup effects.
9. **Bounded retention.** Proposed policy to settle in the spec: automatically prune terminal runs and their events 90 days after terminal time, on startup and periodic sweep; additionally cap terminal runs globally at 100,000, evicting oldest terminal first with stable ID tie-break, transactionally on closure as well as sweeps. Disclose possible earlier eviction and background-agent deletion. Retention pruning never removes active runs; agent deletion removes them as lifecycle cleanup. Bound active-run history to the newest 10,000 events: transactionally evict oldest events as new ones arrive, retain the current visit and metadata needed for correct future transitions, and mark the timeline and analytics as incomplete with an explicit retained-history cutoff. Do not block valid transitions or exits at the cap or invent durations for evicted visits; chart only retained, measurable visits and disclose partial totals. Bound note/reason text to 4 KiB UTF-8 and reject oversize input without truncation. Persist a nondecreasing sweep cutoff to prevent clock rollback extending age indefinitely. Manual deletion coexists with automatic pruning; neither touches execution-evidence retention or replay fences. Confirm proposed limits against operational needs before implementation.

## Implementation order

1. Author the spec and mutation inventory; define operation identity, notes/reasons, status, deletion races, retention, agent-deletion cleanup, prompt association and analytics contracts first.
2. Implement migration, store schema and atomic lifecycle mutations, snapshotting, idempotency and retention. Audit all binding writers; preserve generation fences and effects ordering.
3. Integrate managed tools and guidance, REST endpoints and post-commit refresh; implement the header action, journal modal, analytics and confirmed deletion using existing patterns.
4. Implement fast Playwright E2E tests with real browser, WebSocket, REST, proxy, router and SQLite and deterministic mock LLM. Use focused store concurrency/fault-injection tests as supporting evidence. Retire redundant internal-mock integration tests only when actual coverage replaces them.
5. Run all mapped E2E cases plus affected return, goals, background and deletion regressions, Go tests/build and web checks. Independently review migration, atomicity, retention, privacy and races; record actual results and unresolved failures. Land only after acceptance, without unrelated changes.

## E2E scenarios to map in the spec

- Activation; explicit, implicit, cross-workflow and self transitions; exit with and without reasons; ordered timeline and visit durations. Rejected/stale attempts change neither binding nor journal.
- Agent proactively records a note and also responds to a human request; notes survive reload. Test blank, oversize, no-active and unauthorized cases, restricted tools and no automatic note from ordinary chat. Verify each transition and exit prompts for a human-facing entry, distinct from an optional reason; after exit the entry attaches to the correct run and event. Verify synchronous prompt content and event association after exit and after a later transition; an unwritten entry is not reported as present. Do not assert durable delivery after a crash.
- Interactive, background and scheduled runs appear; agent scope and pagination are correct; the selected-run chart aggregates revisits by workflow/state ID, separates same-named states across workflows and handles an active visit correctly. Verify header action, unchanged badge management, visible per-visit durations and expansion, empty/loading/error, text escaping, keyboard/narrow-screen behavior, and WebSocket disconnect followed by REST refresh. Add deterministic visual/screenshot coverage of the sci-fi vertical scrollable timeline at desktop and narrow widths, including visible durations and scrolling.
- Cold restart and repeated migration preserve a single active run; legacy bindings get one marked synthetic start and no invented history. Renamed agents and renamed or deleted definitions retain snapshots for surviving runs. Deleted agents have no accessible journals or orphan route.
- Deactivation, replacement and state/workflow deletion record outcomes matching each actual successful binding path; agent deletion and background cleanup remove all journals for the deleted agent without affecting other agents; failed startup creates no phantom run. Concurrent transitions, stale bindings, injected transaction failure, commit-then-retry and competing admin operations prove atomicity and no duplicate events.
- Completed-run confirmation/cancel, success and reload, selected-run chart update, unrelated runs unchanged; direct API, double delete, active-run rejection and races against completion and automatic pruning. Agent deletion removes active and terminal runs ; execution evidence follows its separate policy.
- Controlled clock and cap tests cover expiry boundary, deterministic oldest-first eviction, startup/periodic sweep, rollback, active-run rolling eviction, incomplete-history disclosure, accurate retained-visit analytics and continued transitions/exit beyond 10,000 events, concurrent writes/deletes and restart. Verify SQLite and UI agree.
