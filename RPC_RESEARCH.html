Scope and evidence standard

This page answers the technical questions in RPC_REQUIREMENTS.html. It is not a product specification and does not override the final product defaults.

Verified source scope
  • Stock subprocess protocol: installed pi --mode rpc 0.85.0. The readable 0.85.1 checkout is exact source-map evidence for the protocol-critical installed files named below.
  • Local integration: the checked-out Mailbox V2 router, React Web UI, mecha-messaging, mecha-goal, tmux tooling, and the configured pi-subagents fork.
  • Provider integration: built-in Pi providers plus the inspected npm package pi-cursor-sdk 0.3.6. No account, credential, or billable provider call was inspected or run.
Evidence rule

Validated reports override primary reports. A claim appears as verified only when the validator supported it or narrowed it without changing the conclusion. Runtime behavior not captured in an experiment stays open even when source strongly suggests it.

Reading this page: “Verified” describes current source, tests, or controlled smoke evidence. “Recommendation” is a design implication. “Unknown” is a question the reports did not prove. “Required experiment” has a bounded setup, action, and pass condition.

02

Executive findings

What RPC gives us

Pi can run headlessly as a JSON Lines process. The controller can launch it without tmux, send prompts, read live assistant and tool activity, obtain JSON state, manage persisted sessions, compact, and choose from Pi’s current available-model snapshot.

What the stock wire does not give us

Stock RPC does not expose provider login, logout, auth status, a controller-defined callable tool protocol, mailbox envelopes, reminder or goal transport, a subagent watch API, or a normal shutdown command.

What that means

The router still needs durable process/session supervision and separate history storage. Router-managed agents use a new thin extension; tmux remains the supported legacy compatibility path for this delivery. Its future deprecation and removal are product direction, not current implementation scope. The router host must not mistake standard tool events for a controller tool callback.

Plain English: RPC is a good pipe to a headless Pi session. Router-managed agents get a thin extension that forwards their registered tool calls to the router; tmux remains the supported legacy compatibility path in this delivery, using its existing extensions and protocol. The router owns the tool logic in the new path.

The public protocol is JSON Lines: one JSON record per LF-delimited line over stdin and stdout. Stderr is diagnostics. A response ID correlates a command response, but ordinary events have no run or turn ID. Controllers must serialize state-changing calls themselves.

04

Can RPC expose router-provided tools to Pi?

Verified limitation

Not with stock RPC alone. Pi emits LLM tool lifecycle events after Pi has found and executed a registered in-process tool. The controller cannot register a tool, receive a supported tool request, or send a result back against toolCallId. That ID is observation correlation only.

Made-up register_tool, tool_request, or tool_response records are not part of the command union. A controller cannot turn a reported tool call into a router callback.

Selected router-managed direction

Every fresh router-managed Pi process must atomically accept the full bounded, versioned, canonically hashed startup manifest for the 16 required baseline tools and no more than 32 definitions before it becomes ready or starts its first model turn. The thin extension registers those data-defined definitions; each call emits a namespaced JSON control request in a custom Pi session message and returns without waiting. The router validates the request and runs the corresponding internal handler. Until a separately accepted add-only update protocol exists, the extension accepts exactly one startup manifest and rejects later delivery after the first non-command prompt. That protocol may add only a previously unused tool name; it cannot remove, replace, or mutate an installed definition in place. Existing extensions and their WebSocket protocol remain the supported legacy tmux path for this delivery; their future deprecation/removal is not current implementation scope.

Conditional isolated proof; router proof still open. A custom session message carries the tool name, request ID, arguments, and customType/details payload in Pi’s fixed event envelope. The isolated mechanism passed for request, result, error, malformed payload, and replay rejection without a model turn. It remains one-way: fire-and-forget calls end after local emission, and an async tool never waits for its result. An actual router must still deliver a later correlated result/error and prove its wiring, lifecycle fencing, and idempotency. extension_ui_request/extension_ui_response is not the chosen synchronous tool transport.

What makes the thin-extension control bridge possible — and bounded

When loaded under the normal extension and project-trust rules, RPC binds an extension in-process with mode: "rpc". The thin extension can register every required LLM-callable tool. Its execution still emits the normal tool_execution_start, tool_execution_update, and tool_execution_end events; these are observation, not router callbacks.

Isolated mechanism verified: the probe emitted mecha.control.request.v1 through pi.sendMessage(). A later standard RPC prompt invoked a reserved extension application command. Pi dispatches that command to the extension before ordinary input/model processing; the extension validates the JSON and request correlation, then calls pi.sendMessage({triggerTurn:false}) to create the typed internal custom session message. Exact fixed message_start/message_end envelopes and nested JSON details were observed; malformed, unknown, and replayed IDs were rejected. No Pi model turn, UI dialog, user/assistant message, tool call, auth validation, or paid request occurred in the isolated runs.

pi.sendMessage() can append a custom session message with arbitrary customType, content, display, and details. The proposed thin-control request uses that fixed session/event envelope, with a namespaced type and strict JSON request body. details stays outside model context; any content is later model context and must be safe and bounded. pi.appendEntry() is only an audit/state alternative because it does not enter model context. Neither API creates an arbitrary top-level RPC command or event type.

Precise boundary: the command is reserved by the thin application extension, not by Pi; Pi can suffix duplicate command names, so production needs an owned extension plus collision/startup check. The inbound RPC record remains a standard prompt with string message content. It is not itself an arbitrary customType or custom-session envelope; only the extension creates the typed internal custom session message after validation. The ordinary prompt response means accepted/queued/handled, not result delivery. The router must wait for the concrete custom message_end receipt. Custom session messages remain one-way; no waiting tool gets a returned value.

Still unproven outside isolated Pi: no Mecha router process, target selection, socket, direct pipe, reconnect, or real internal handler was exercised. The probe’s issued-ID state is session-local and is lost on extension reload/switch/new/resume/fork. It is not restart-safe or end-to-end idempotent: persist/reconcile router-owned request state, generation fences, and completed-result receipts before claiming retries are safe. Input records dispatch concurrently, so serialize future awaited state mutation. Streaming deferral with triggerTurn:false is source-backed but was not live-tested; prompt acceptance is not an acknowledgment.

The UI bridge is fixed: dialog requests are select, confirm, input, or editor; responses are a string value, boolean confirmed, or cancelled:true. notify, status, widget, title, and editor-text calls are one-way UI notices. They do not create a generic callback, and this dialog bridge is not the control transport.

Late dynamic tools: validated Pi behavior and production boundary
Installed Pi mechanism

Pi 0.85.0 permits an extension command to call pi.registerTool() after startup and refreshes the current session. The isolated harness installed one tool, and the next local fake-provider request included its expected schema. It also showed same-extension replacement, first-extension-wins behavior for the tested cross-extension collision, and active-set deactivation without unregistering.

Not production proof

The harness used raw schema through Type.Unsafe. Its array bounds were wrong, primitive coercion occurred, and some string/number bounds were optional. Its dynamic closure only returned fixture text. It did not emit a router control request, include the dynamic tool name or tool-call ID in one, accept a later completion, or exercise a router.

Validator-controlled disposition: late dynamic registration works in Pi 0.85.0 and the next fake-provider request sees the tool. A production-safe manifest design was not proven. Keep the stock-RPC limitation: an external controller still cannot register a tool directly or send a generic tool_response; only the fixed trusted extension can register and execute a dynamic definition.

Where the two isolated results compose: the dynamic harness and the validated control roundtrip show that a fixed extension command can receive a manifest through a standard RPC prompt and emit a correlated custom acceptance/rejection record with triggerTurn:false. The meaningful receipt is the custom message_end, not prompt acceptance. They do not prove a dynamic tool closure sends a router request or that a later custom message can replace its already returned tool result. Full router end-to-end control, delivery, idempotency, and streaming behavior remain unproven.

06

Current router and Web UI behavior

What exists
  • A durable Mailbox V2 router for already-connected WebSocket clients.
  • Message queue, reminders, prompt templates, pairwise conversation messages, goal-control relay, and native-subagent lifecycle storage.
  • tmux window provisioning and keystroke controls. This is a terminal-management path, not direct Pi RPC launch.
  • A Web UI for ordinary pairwise chat, connected-agent status, model/goal/reminder/inline-tool controls, and templates.
What does not exist yet
  • In this checkout’s declared router manifest/dispatcher, no managed-agent launch, restart, terminate, reset-context, runtime-state, provider-authentication, or complete-activity API exists.
  • In the inspected migrations and transport code, no durable managed process/session registry exists.
  • In the inspected Web UI source, no launch form, runtime source badge, JSON state popup, global default-worker model setting, quiet/complete toggle, or provider login UI exists.
  • In this checkout, no direct RPC mailbox-injection path exists. Current delivery is extension WebSocket delivery plus Pi-session checkpoint acknowledgment.

Current quiet-history limit: the current router retains 200 messages per unordered participant pair and prunes messages older than 30 days. The browser mirrors the same per-peer 200-message and 30-day bound. This is ordinary two-way conversation history. It is not a dedicated quiet history and does not prove the required “explicit agent send-message tool directly to Wolfgang” filter.

Why the existing logs and history cannot become complete history

The router JSONL log is diagnostic output: it rotates after 24 hours or 16 MiB, removes rotated logs older than 48 hours, and has a 32 MiB retained-file bound. It has no activity-history API. It cannot serve a durable complete history.

Conversation messages cover mailbox conversation only. They do not cover all tool calls, compactions, errors, or process transitions. The required quiet and complete histories need separately bounded durable representations. Complete history must retain at most 200 total activity entries. A complete-history entry may reference a quiet message, but complete-history pruning must never evict quiet history.

Settled requirement constraints the final specification must preserve

These are product requirements, not evidence that the current checkout implements them. They close false passes in otherwise sound research recommendations.

Managed HTTP and WebSocket authorization: the router does not use Origin or host origin as authorization. Requests may come from any host or origin that can reach the router, and non-browser clients without Origin remain supported. This does not change bind, listen, exposure, Tailscale, or public-network configuration.

Browser-session authentication, request correlation, CSRF protection for cookie-based state-changing requests, WebSocket session authorization, and secret redaction establish authority. No new authentication framework is required. Acceptance must show valid authenticated requests from two unrelated HTTP(S) origins succeed, while missing or invalid session or CSRF proof fails independently of Origin.

Thin-extension migration: compatibility inventory

This is the exhaustive legacy compatibility inventory for the router-managed thin extension. Its mandatory startup manifest registers all 16 required baseline tools and no more than 32 definitions, emits structured JSON controls, and leaves behavior in router handlers. A later supplemental manifest may add only a previously unused tool name; it cannot remove, replace, or mutate an installed definition. Existing mecha-messaging, mecha-goal, and their protocol remain the supported legacy tmux compatibility path for this delivery. Their future deprecation/removal is product direction, with no current migration or removal work. Matching names is not enough.

Current integration result: isolated mechanisms passed; router path unproven. The thin extension can register in-process tools; Pi 0.85.0 can also late-register an extension-owned dynamic tool that appears on the next fake-provider request; and an isolated application-command/custom-message roundtrip passed. The router still needs strict request validation, real target/pipeline wiring, generation correlation, durable result receipt/idempotency, the mandatory startup-manifest ready gate, and the raw compiler/immutable-name boundary for any separately supported post-start add-only update. The custom-message leg is one-way.

Legacy commands and in-Pi hooks: unchanged for tmux, allocated for thin mode

Goal commands: goal, goal-lock, goal-snooze, goal-snooze-turn-limit, goal-snooze-budget, and goal-snooze-budget-refill. Messaging commands: mecha-parent-message, inline-tools, and mecha-reply. They remain existing tmux behavior, including root-session/tmux identity qualification and the current Cursor-document omission.

The current direction requires all 16 tools in the thin extension; it does not make a legacy slash command a substitute for its tool. In thin mode, the extension is limited to registering tools, validating a request envelope, emitting custom request messages, and handling an owned application command that turns a later router result/error into a triggerTurn:false custom message. Router handlers own the business behavior and durable state. Any thin slash-command surface must be specified separately, collision-checked at startup, and not copied by accident.

Migration seams that must be allocated to router handlers: inbound/mail acknowledgment; activity and lifecycle state; model/current-model control; goal state, evaluation, and control fencing; reminders; inline credits; recall; compaction policy/handoff; diagnostics; native-child projection; history retention; outstanding-request ownership; session/generation fencing; and completed-result receipts. The thin extension retains only the minimal Pi lifecycle hooks needed to transmit requests and consume valid later control results.

Other validated parity corrections
  • Persisted Goal is not wire Goal: when goal off runs, persisted internal state can retain the old goal text and optional snooze/rearm fields. Only the wire projection normalizes disabled state to {enabled:false, goal:""}. Any router-managed integration needs a separate persisted-state decoder or normalized persistence. Do not deserialize goal-state as wire goalState.
  • Sentinel model boundary is inconsistent: router/schema sentinel.model is a string. Messaging types and passes an object-shaped ModelInput. The existing test preserves that forwarding mismatch. It does not prove native Pi accepts it. Pick one wire representation, translate or validate at the router-to-native boundary, and use a real native service test.
  • Loopback policy differs: operational HTTP accepts localhost, 127.0.0.1, and ::1. The canonical mailbox client and recall path accept literal 127.0.0.1 or [::1], not localhost. The thin router-managed path needs one documented rule and client, recall, and operational tests.
  • Schema validation has two contracts: the published JSON Schema says additionalProperties:false. The Go server intentionally sanitizes unknown additive client fields before validating. A schema-only consumer cannot infer that tolerance. Document which fields are stripped and which remain strict.
  • There is no authoritative generated tool manifest: runtime TypeScript schemas and selected tests are the authority. mailbox-client.js is generated client code, not a tool/command manifest. Current human documentation omits goal_snooze and Messaging commands. A generated or snapshot registration contract is required.
Validator-corrected current tmux delivery finding

The canonical Messaging client omits ack_confirmation: "correlated_v1". The router then omits top-level incarnation data. The published message schema requires incarnation data, so every non-correlated router message frame is schema-nonconforming.

The primary report overstated the liveness impact. A one-item delivery can still be acknowledged by message ID, attempt, and deadline because the coordinator permits a missing incarnation. The real issue is a weaker ID-reuse fence and a production client that does not negotiate its published correlated contract. The isolated end-to-end test patches registration, so it does not prove the normal client path.

This is an unchanged tmux-path finding, not a claim that the thin direct path repairs it. The thin path does not activate that WebSocket protocol. Its own request/result correlation must be proven separately, and it must not be called delivery-equivalent merely because it bypasses the current client.

Required current-agent behavior: a successful login or logout changes that shared context for every router-managed agent’s future work. Launch and router-directed model selection use only models available from the changed shared context. This is a product requirement awaiting implementation verification, not a claim that upstream Pi performs this orchestration itself.

How model availability actually works
  1. Pi registers built-in, configured, and extension providers into a complete catalog.
  2. Pi checks which providers are configured and creates an available snapshot.
  3. pi --list-models, RPC get_available_models, normal model fallback, and RPC exact set_model use that available snapshot.
  4. An explicit CLI model can search the wider registered catalog for first-time key setup. RPC set_model cannot. It accepts only an exact current snapshot row.

Availability is not a successful provider request. Entitlement, key validity, quota, network, and provider policy can still fail. An out-of-band credential-file edit does not automatically refresh a running RPC snapshot; use a real runtime refresh/restart or an applicable extension operation.

The router has durable mail, conversations, reminders, goal-control, and native-child records. Session semantics: --session-id selects an exact project/session-directory-scoped Pi session and creates it if absent. A router can use it for controlled continuity. RPC new_session cannot accept a caller-chosen ID, so it cannot itself meet the product reset requirement.

Dynamic-manifest runtime boundary: late definitions disappear after a session replacement and a process restart. If any startup-manifest definition changes, start a fresh Pi runtime, preserve the agent’s required session ID when this is an ordinary restart, and replay the complete manifest before any model request. Do not try to reconcile Pi’s registry in place.

Router restart is the hard boundary: a new router does not regain old stdin/stdout pipes by knowing a PID. It needs a deliberately tested ownership protocol: controlled process-group replacement with duplicate fencing, or a durable per-agent host with a reconnectable control channel.

Crash-loop policy: supported shape, not a validated number

No exact restart count, window, healthy-period reset, or backoff number was validated. The primary report’s numerical proposal is not evidence-backed and must not be presented as researched behavior.

Smallest explicit policy shape: define an unexpected-exit classifier; persist exit timestamps and a finite threshold within a named window; define a deterministic backoff schedule; define when healthy time resets the budget; exclude intentional stop/restart/reset/terminate; record a blocked state and last exit error; and specify how an explicit user restart affects the block.

The final specification selects three unexpected exits in two minutes, one-then-five-second backoff, and a ten-minute healthy reset. Those are product choices, not source-validated Pi behavior; the selected policy still needs implementation acceptance tests.

tmux boundary and direct delivery boundary

This delivery keeps tmux as the supported legacy compatibility path. Existing tmux agents keep the current extensions and connect through their WebSocket/lease protocol. The router’s tmux restart sends keystrokes and does not know the actual executable, PID, provider, or durable session mapping. It is not a safe generic process supervisor. Product direction is eventual tmux deprecation/removal; no timeline, migration, or removal work is part of this delivery.

A router-managed Pi worker instead loads only the thin extension. A tool’s custom session message is a one-way request to the router, not a mailbox receipt or synchronous result. The isolated Pi mechanism verified a later result/error through a standard RPC prompt that invokes a thin-extension-reserved application command before model processing; after JSON/correlation validation, the extension creates the typed internal custom session message with triggerTurn:false. The inbound RPC prompt is not itself an arbitrary customType. This does not prove the actual router route. Before adoption, prove real target selection/pipes, command ownership, streaming behavior, stale-generation rejection, durable receipt, and idempotent retry; otherwise scope the smallest needed change.
