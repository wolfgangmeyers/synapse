# Spec: Background Bash Jobs

- **ID**: `SPEC-BACKGROUND-BASH-001`
- **Status**: `Draft` — implementation exists; acceptance incomplete
- **Domain**: `AgentManagement`
- **Target E2E Suite**: `tests/e2e/background-bash.spec.ts`, `tests/e2e/background-bash-promotion.spec.ts` and `tests/e2e/background-bash-claude-child-wait.spec.ts` (partial)

## 1. Intent & User Outcome

**Platform limitation:** Background bash launches are supported only on Linux. On other platforms, root and worker launch requests return an explicit unsupported-platform error before starting a shell or creating a job; foreground Bash retains its existing behavior. See [platform limitation](background-bash-platform-limitation.spec.md).

On Linux, a managed root, worker or embedded subagent can start a shell command without blocking its turn, check its progress, and stop it. The agent receives a completion notice, while the conversation header shows the selected agent's jobs. Background jobs are not subagents. The promotion contract below extends regular embedded Bash promotion to root, worker and subagent roles; native Claude Bash is outside its scope.

## 2. Core Invariants

1. On Linux, the router owns each job and its lifecycle. Authority and ownership come from the trusted managed binding, never tool arguments. Root, worker and embedded subagent owners can use `launch_background_bash`, `list_background_bash_jobs`, `get_background_bash_job` and `kill_background_bash_job` for their own explicit or promoted jobs; they cannot access other owners’ jobs. Subagent explicit launch and controls are required but not yet established by the staged implementation. Stale bindings and other owners cannot inspect or affect jobs.
2. All four operations bypass inline-tool enablement and inline allowance accounting, including when the allowance is zero. They remain subject to ownership and the separate polling budget. Regular Bash retains its existing invocation policy and accounting, including when promoted. No new command-content restriction is imposed.
3. Reads are nonblocking snapshots. Results distinguish running, successful, nonzero exit, killed, timed-out and uncertain outcomes; an exit code is reported only when known. Output is bounded and truncation is visible.
4. Completion uses the ordinary managed notification and wake path, including its existing delivery behavior. A notice identifies the job and includes its exit code when known, otherwise an honest status. No durable or exactly-once delivery is promised.
5. Background job list and get share a **separate** per-session-lane pool, surviving transient session bindings and subagent child terminations, initially and maximally three credits, replenishing continuously at one credit per minute. `list_background_bash_jobs` always costs one credit; `get_background_bash_job` on a running or unresolved uncertain job costs one, while get on a terminal job is free. Accounting is atomic across concurrent and alternating calls. Launch, kill, wait, notifications and UI updates do not consume credits; child launch, termination or replacement does not reset an existing lane balance. The existing subagent read pool and its contract are unchanged.
6. Job concurrency, captured output, list/response size and terminal record age and count are bounded. Terminal records and their output are pruned automatically. Current implementation limits and cleanup triggers are documented below; their full acceptance coverage is incomplete.
7. Kill, timeout, owner termination, binding replacement and router shutdown use safe process ownership and cleanup. A process must not be signaled after its identity can no longer be verified; cleanup or exit uncertainty must not be represented as success or a fabricated exit code. No durable crash recovery or exactly-once execution is promised.
8. The compact, accessible conversation header shows only the selected agent's jobs and status, updating live. It does not add output or kill controls. Browser transport retains permissive, non-credentialed cross-origin behavior; Origin is not authority.

## 3. User Scenarios (Behavioral Contract)

### Automatic promotion of regular Bash (proposed; acceptance pending)

On Linux, a regular embedded managed root, worker or subagent Bash command still running at its existing foreground timeout is automatically promoted to an existing background-job handle. The timeout no longer kills that command: the **same process** continues without a retry or relaunch. The proposed design gives it a 10-minute background lifetime measured from promotion (not a separate user requirement), after which existing timeout and safe cleanup rules apply. Fast commands retain their ordinary foreground result and existing inline policy and accounting. Native Claude Bash is outside this change. The non-Linux limitation above remains in force.

The promoted job uses existing ownership, bounded output, lifecycle and polling rules. Its owner can inspect and stop it; list and running or uncertain get consume the existing background read budget, and terminal get is free. The subagent’s trusted identity must scope its jobs; it cannot inspect or stop another owner’s job. The wait/wake behavior below is a required outcome, not a prescribed new API. The current implementation names its wait tool `wait_background_bash_job`.

### Scenario: [BB-PROMOTE-001] Slow command continues as the same process
- **User Goal**: Continue slow work without blocking or repeating side effects.
- **Given**: An embedded managed root, worker or subagent on Linux starts a permitted regular Bash command that remains running past its foreground timeout.
- **When**: The foreground timeout is reached.
- **Then**: Bash returns a background handle and the same process continues, without being killed or restarted. Exit racing the deadline produces one consistent foreground or background outcome, without duplicate completion results or notices. Captured output before and after promotion is available under existing bounds. The owner can inspect and stop the job, subject to the polling budget. Completion is reported to the owner. If still running 10 minutes after promotion, the job is timed out and cleaned up under existing rules.

### Scenario: [BB-PROMOTE-002] Fast commands and policy remain unchanged
- **Given**: An embedded root, worker or subagent invokes regular Bash.
- **When**: The command finishes before its foreground timeout, or the existing invocation policy denies it.
- **Then**: The fast command returns its ordinary foreground result without a background job. A denied invocation does not start or promote a process, and existing inline policy and accounting remain in force.

### Scenario: [BB-PROMOTE-003] Promotion fails
- **Given**: A regular embedded Bash command reaches its foreground timeout on Linux, but a job handle cannot be established, for example because capacity is exhausted.
- **When**: Promotion fails.
- **Then**: The failure is reported honestly, without rerunning the command or claiming a usable handle. Cleanup follows safe process ownership rules, retains a sole reaper even on failure, and reports any uncertainty within a bounded time. A group is signaled only while its identity is verified; an unverifiable group is not signaled.

### Scenario: Foreground cleanup ownership and admission
- **Given**: A Linux foreground Bash command may later need promotion or cleanup.
- **When**: Its owner starts it, is retired, cancels, or the manager shuts down.
- **Then**: The manager reserves one of 32 separate foreground ownership slots before the shell starts; background jobs and retained records do not consume these slots. Admission failure starts no shell. At the deadline, promotion atomically checks background running and record capacity; if unavailable it reports failure and safely cleans up without rerunning. A failed background admission does not evict unexpired terminal records. A fast successful command releases its reservation without creating a visible job. Retirement and shutdown fence admission and initiate cleanup of admitted commands. If cleanup or group verification is uncertain, the unreaped leader and its capacity remain manager-owned, visible as uncertain, and retried without signaling an unverified group or starting a second reaper. The caller receives an honest error within its deadline; shutdown reports incomplete cleanup rather than discarding ownership. Identity lookup is bounded for the foreground caller and cancellation or shutdown releases launch admission. A blocked lookup remains counted and cannot spawn overlapping retries; the shell stays unreaped and uncertain until identity is verified. Failed identity verification remains tracked and is retried through shutdown without signaling or reaping an unverified group. Once identity is verified, signaling retries run concurrently with the sole waiter. A failed durable orphan-record removal remains visible as uncertain and retains capacity even if the process was reaped. The manager retries removal without reaping or signaling again; recovery releases capacity and preserves the original wait outcome, including output drain errors. If an uncertain background completion notice was attempted, recovery attempts one distinct updated notice with the resolved outcome. Shutdown stops retries and reports incomplete cleanup if removal remains unresolved. A post-reap output drain failure is reported without starting another waiter.

### Scenario: Foreground output exceeds the limit
- **Given**: A foreground command exceeds the output limit.
- **When**: It is still running when overflow is observed.
- **Then**: Excess output is drained and discarded while the command continues. If it exits before the foreground deadline, its actual exit status and bounded output are returned with a truncation notice. If it remains running at the deadline, it is promoted normally with the same process and truncated output. Cancellation, owner shutdown and cleanup uncertainty retain their ordinary ownership and safety rules.

### Scenario: [BB-PROMOTE-004] Owner waits for shell completion
- **User Goal**: Pause without polling and resume the task when the shell finishes.
- **Given**: An embedded root, worker or subagent owns an explicitly launched or promoted job and has no other work to do until it finishes.
- **When**: The owner waits before, during or after the job completes, fails, is killed or times out, or the wait is canceled or the owner shuts down.
- **Then**: Completion cannot be missed at the wait boundary: the owner resumes with an indication identifying the job and outcome and can retrieve the terminal result without a polling-credit charge. Wait itself is free. Cancellation or owner shutdown unblocks the waiter; owner shutdown cleans up its job under existing safe cleanup rules. Waiting alone does not report a subagent as finished to its parent. An ordinary completion notice is attempted whether or not anyone waits.


### Scenario: [BB-STEER-RACE] Short completions during active tool calls
- **Given**: A Claude-managed agent is executing a turn with background shell launches.
- **When**: Short jobs complete and their notices are steered into the active turn while further tool calls execute.
- **Then**: Checked notices and tool results remain ordered in the same conversation, the turn completes without an embedded head mismatch, and successfully executed launches are not reported as unknown.
- **Verification**: `tests/e2e/background-bash-steer-serialization.spec.ts` — `short completions steer during active launches` checks a completion notice persisted and echoed between a completed launch and later launches in the same held turn. Its fixture barrier is between operations; it does not establish overlapping persistence or deterministic lock contention. General Claude mail and notice persistence ordering is specified in [CC-021](claude-code-workers-spec.md); `TestClaudeCheckedInputContendsWithExecutingTool` deterministically observes input waiting on the persistence mutex while a reminder tool executes through the shared bridge and store, not the full background-job lifecycle. The E2E checks only the available retained 65,536-character stderr tail before fixture shutdown, not the complete stderr stream or shutdown output; older errors may have been evicted. Acceptance remains pending.

### Scenario: [BB-REST-ERROR] Managed agent projection cannot be sampled
- **Given**: A managed agent list or detail request needs a background-job snapshot.
- **When**: Its owner or store snapshot fails.
- **Then**: The entire request returns an internal HTTP error, not a successful partial projection or null jobs. Snapshot work uses the request context.


### Scenario: [BB-001] Root and worker launch a job
- **User Goal**: Start useful shell work without waiting for it to finish.
- **Given**: A managed root, worker or embedded subagent on Linux has a valid command and an active binding.
- **When**: It launches the command without a timeout override.
- **Then**: Launch does not wait for command completion and returns an identifiable job; the command may finish before the response arrives. The default timeout is 10 minutes. The command uses existing managed Bash working-directory and environment behavior where applicable. When the shell exits, even successfully, remaining members of its verified process group are killed before the shell is reaped; a child started with `&` must not be assumed to continue. Detached descendants are not guaranteed to be contained. Available output and the actual exit code are visible in a later snapshot, and completion is notified.

### Scenario: [BB-002] Timeout override and invalid launch
- **User Goal**: Limit a job's runtime and understand launch failures.
- **Given**: A managed root, worker or embedded subagent supplies a command with or without a timeout override.
- **When**: It supplies a valid short override, or invalid input, an invalid working directory, or a command that cannot be started.
- **Then**: The timeout deadline is fixed at launch admission and is not extended by startup or identity lookup. A job exceeding a valid timeout is stopped as soon as safely possible and reported as timed out, with its process tree cleaned up where possible and exit or signal information only when known. Invalid input and start failures are reported honestly without a leaked job or reservation. If identification or cleanup fails, the failure and any uncertainty are reported; cleanup must not risk signaling an unrelated process, and a successful signal alone does not prove detached or concurrently forked descendants are gone. A blocked cleanup may cause bounded shutdown to report an error. The optional `timeout` is an integer number of seconds from 1 through 9,223,372,036 inclusive; omission defaults to 600 seconds. Zero, negative, fractional, non-numeric and larger values are rejected.

### Scenario: [BB-003] Snapshot and output
- **User Goal**: Inspect work without blocking.
- **Given**: An owner has multiple running or completed jobs, including a command producing stdout and stderr and exiting nonzero.
- **When**: The owner lists jobs and gets individual job snapshots.
- **Then**: The list contains only owned jobs and metadata, including current state and truncation, but omits output. Individual get snapshots include available output; the nonzero job shows its actual exit code. Output exceeding the capture bound is visibly truncated while execution can finish. Unknown job IDs return a clear error.

### Scenario: [BB-004] Kill and completion race
- **User Goal**: Stop an owned job without affecting unrelated processes.
- **Given**: An owner has a running job, and another job may finish concurrently with a kill.
- **When**: The owner kills a job, repeats the kill, or races a kill with completion.
- **Then**: The owned process tree is stopped and reaped when safely possible; unrelated processes are not stopped. If cleanup cannot be confirmed, the job remains uncertain and cleanup continues while identity can be verified; no signal is sent after identity is lost. If an explicit stop fails and the job remains unresolved for three seconds, the job is marked uncertain with the cleanup error and a change notification is published. A later confirmed cleanup clears transient cleanup errors and reports the observed terminal state. Repeated kill does not invent a new outcome or exit code.

### Scenario: [BB-005] Inline exemption
- **User Goal**: Manage background work even when inline tools are unavailable.
- **Given**: Inline tools are disabled and the owner's inline allowance is zero.
- **When**: The owner launches, lists, gets and kills a background job within its read budget.
- **Then**: All four operations work without debiting inline allowance. Ordinary foreground Bash remains subject to its existing policy.

### Scenario: [BB-006] Subagent and owner boundaries
- **User Goal**: Keep jobs accessible only to their authorized owner.
- **Given**: A root and worker have active bindings, a subagent is running, and a job belongs to one owner.
- **When**: Root, worker and subagent use the four operations on their own explicit and promoted jobs; the subagent attempts to access another owner’s job through discovery and direct or alternate dispatch; another owner or stale binding attempts to read or kill the job.
- **Then**: Authorized root, worker and subagent operations succeed for their own jobs. Subagent attempts to access another owner’s job are denied before effects, and the other owner and stale binding cannot inspect or kill the job. Subagents can also launch explicit jobs and list, inspect and stop their own explicit or promoted jobs. Hiding tools alone is not sufficient denial.

### Scenario: [BB-007] Bounded polling
- **User Goal**: Check progress occasionally without a busy polling loop.
- **Given**: An owner has a full three-credit background-job read pool and a running job.
- **When**: The owner alternates list and running or unresolved uncertain get, including concurrent requests, until credits are exhausted, then waits for refill and gets a terminal job; children terminate or are replaced on the same session lane.
- **Then**: At most three credit-consuming reads succeed before refill; exhaustion clearly suggests awaiting completion or doing other work. One credit replenishes per minute up to three. Terminal get is free; launch, kill, wait, notices and UI updates do not debit this pool. Child termination, replacement or launch does not replenish or reset an existing lane balance. The existing subagent read budget is unaffected.

### Scenario: [BB-008] Completion notice
- **User Goal**: Learn when background work finishes without polling.
- **Given**: An explicit or promoted job owned by a root, worker or subagent completes, fails, is killed or times out, whether or not its owner waits.
- **When**: The ordinary managed notification path handles completion.
- **Then**: It attempts a notice to the owner with the job ID and known exit code, or an honest status if unknown. Existing delivery behavior applies; an enqueue failure is logged without claiming successful delivery or adding a background-bash-specific retry.

### Scenario: [BB-009] Conversation header activity
- **User Goal**: See background activity for the agent being viewed.
- **Given**: Different agents have different jobs and the conversation is open in a browser, including root and worker agents and an arbitrary cross-origin frontend. Different router instances can have the same agent ID.
- **When**: Jobs change state or the user switches selected agents.
- **Then**: The compact accessible header widget shows a job count without listing IDs in the header. Opening it reveals the selected agent's full job IDs and current statuses in a read-only dialog that updates live, without leaking other agents' jobs. Closing it returns to the compact header. A router projects only jobs owned by its own manager and current binding. It provides no output or kill controls and does not consume tool polling credits.

### Scenario: [BB-010] Bounds and cleanup
- **User Goal**: Run jobs without unbounded resource accumulation.
- **Given**: The documented concurrency, output, response and terminal-retention limits are reached or terminal records expire.
- **When**: Jobs are launched, finish, fail, time out or are killed, and automatic cleanup runs.
- **Then**: Capacity failures are clear; output and responses remain bounded; expired or excess terminal records and associated output are automatically pruned according to the documented triggers. Active jobs and ordinary notifications follow their applicable policies. Processes, handles, timers, pipes and reservations are released on every outcome, subject to honest reporting of cleanup uncertainty.

### Scenario: [BB-011] Ownership transition and shutdown
- **User Goal**: Avoid orphaned jobs and stale authority.
- **Given**: A job is running when its owner terminates, its binding is replaced, or the router shuts down.
- **When**: Cleanup and a competing stale operation or lifecycle update occur.
- **Then**: A competing launch for the retiring owner is either included in cleanup or rejected; later stale launches are rejected. Claude workers receive the same cleanup as other embedded workers. A replacement owner is not published until the previous owner's cleanup succeeds. Cleanup uses verified process ownership, and stale operations and updates are fenced. Unresolved identifiable jobs consume capacity and remain a failure on repeated owner cleanup and shutdown, even after normal terminal-record retention would expire. When cleanup cannot verify an already-reaped job after a failed group stop, its terminal failed record releases capacity but reports cleanup uncertainty to owner cleanup and shutdown while that record remains retained; normal terminal age and count limits also bound this warning. No further signal is attempted after identity is lost. A kill racing a completed job observes the completed outcome rather than treating a stale identity check alone as proof of uncertainty. No unverified process is signaled after restart; inability to establish cleanup or exit is reported honestly. Retired owner authority is revoked per lifetime and reclaimed when no longer referenced; past retirements do not exhaust launch admission.

Projection invalidations from job changes and pruning are coalesced into a bounded global dirty signal. Publication reserves a global projection version and samples current fenced owners; changes arriving during publication trigger another pass. Pruning is not deferred by publication backpressure, and reads do not wait for publication. Completion notice admission does not wait for projection publication. Shutdown joins admitted publication and completion work subject to its deadline; a blocked publisher cannot prevent notice admission. A temporary publication or version-reservation failure is retried without requiring another job change. Observers must not regress to an older projection or receive a changed job snapshot under an already published version. Owner replacement cannot expose the old owner's jobs. Shutdown cancels blocked projection work and remains deadline-bounded.

### Shutdown completion

Shutdown accounts for in-flight completion and projection work, including work for terminal jobs. It respects the caller’s deadline and reports a cleanup error if it cannot finish in time; a later shutdown can retry. A blocked cleanup for one job does not prevent cleanup of other jobs or prevent repeated shutdown calls from honoring their deadlines. Process identity must remain verifiable until any pending signal is complete.

Jobs that finish during shutdown, including those stopped by shutdown, use the same fenced completion-notice admission as other jobs. Shutdown joins the attempt while the store remains open, subject to its deadline; admission failure is logged and does not imply delivery or a retry guarantee.

### Scenario: [BB-LIVE-CANCEL] Interrupted live projection and reconnect
- **Given**: A live projection changes while a browser is connected, or a browser reconnects after an unpublished change.
- **When**: Projection or history delivery is canceled or fails, or a new browser connects.
- **Then**: Accepted lifecycle history is recorded before the projection baseline advances; an interrupted batch is retried against the same sampled projection, even if the durable version changes. Browsers that may miss a projection or its history are disconnected so they can reconnect. A reconnect samples through the publication path and receives a version-consistent snapshot; changes committed after that sample converge through later publication, not an instantaneous freshness guarantee. A version reserved for an in-memory change must not label durable data sampled before the reservation.

## 4. Implementation Limits and Retention (current staged implementation, subject to scope audit)

The current router implementation (`router-proxy/internal/managed/background_bash_lifecycle.go` and `background_bash_tools.go`) uses manager-wide, in-memory limits, not per-owner limits:

- At most 32 running or uncertain background jobs, plus at most 32 separately owned foreground commands or failed foreground cleanups. Uncertain jobs keep their respective capacity and are not pruned by ordinary retention.
- Commands are limited to 65,536 bytes. Stdout and stderr share a 65,536-byte capture per job; later bytes are discarded and `truncated` is set. List responses omit output and retain job metadata including the truncation flag; get returns captured output. There is no separate response-byte limit. Record and metadata bounds limit list size, with JSON encoding overhead.
- The background record limit is 256 across the manager, including running and uncertain background jobs; separate foreground ownership slots do not count toward it. On pruning, oldest eligible terminal records are removed to make room for launches. When pruning cannot make room, launch admission reports capacity rather than growing the record store.
- Eligible terminal records and their output expire one hour after finishing. Pruning runs on launch, get, list and completion, and on a one-minute sweeper; kill invokes get after successful completion. UI projection filters expired records but does not itself prune them. Pruning also publishes owner projection changes.
- Linux unidentified-process cleanup attempts a group SIGKILL immediately and makes at most three group-signal attempts total, including the initial attempt, with further attempts at 100 ms intervals while the unreaped child pins its identity. Cleanup is best effort, not containment. Full acceptance coverage remains incomplete.
- Timeout is an integer number of seconds, default 600; the tool accepts overrides from 1 through 9,223,372,036 inclusive and rejects values outside that range or of the wrong type. The internal launch API uses zero to select the default. State is not recovered after router restart.

### Claude child Bash router-crash compatibility

When a Claude child starts a managed Bash command, the command must not execute before its process-group identity is durably available to the existing Claude orphan recovery mechanism. If the router crashes while the command is foreground or after it is promoted to a background job, startup recovery must stop the verified orphan group before admitting replacement Claude work. An unsafe or unverifiable identity must remain fenced rather than being signaled or reported as successfully cleaned up. Explicit background launches by a Claude child must receive the same protection. This preserves the existing Claude process cleanup contract; it does not promise job result recovery or exactly-once execution.
