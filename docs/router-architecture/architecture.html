System / 01

Architecture

The router saves messages in SQLite. When it knows who can receive one, it chooses how to deliver it: a direct prompt to Pi it started, or a WebSocket connection to a supervisor-started worker. Mail can wait in the queue until a recipient becomes active.

Router-started Pi is the main agent (managed root), not a child. Supervisor-started Pi in tmux is a separate worker. Start with the vocabulary if RPC, receipt, or fence is new to you.

Current managed-control flow

The browser calls the router’s HTTP API to control router-started Pi. For provider sign-in or sign-out, it uses /v1/provider-auth and the related action and prompt-response routes. The router records those operations and passes the interaction to its provider-auth coordinator. /v1/models returns available models and the saved default. /v1/settings/default-model saves a validated available model. Launch and restart can also specify a model; the router picks it when starting Pi. managed_http.go:33-117, 126-230, 231-385, 489-572, 663-714

For restart, reset, or terminate, the router records an operation before changing the Pi process. Goal reads and updates call Pi directly through the manager; updates also save an operation. The manager reads and changes inline-tool settings, saving updates in SQLite. The UI reads status by HTTP and receives status updates over /v1/ui-live. That socket displays state; it does not own it. managed_http.go:83-115, 663-806, 1268-1410 ui_live.go:49-68

Anyone who can reach the router can use its managed HTTP controls. There is no authentication on these routes. Cookies, sessions, CSRF tokens, and the request’s Origin do not authorize actions. CORS lets browsers make cross-origin requests; it does not restrict who can use the router. Limit network access to trusted clients. managed_http.go:37-43, 663-668 ui_live.go:49-68

When Pi calls a control tool: Its installed tool sends a hidden request over RPC stdout. The router checks that it belongs to the current Pi process, validates and saves it, then runs the local Python host. The router saves the result and sends it back as a hidden RPC command. Pi appends the result to its transcript and returns a receipt. This control exchange does not send mail unless Pi requested mail.send. rpc-client.ts:21-35 rpc.go:541-568 root_control_manager.go:89-152, 405-418, 531-602 managed_root_control.py:546-555

When Pi starts or changes a child agent: The child service reports changes to mecha-rpc, which sends hidden updates over RPC. The router saves the child state and refreshes the UI. If an update is missing, the router requests a full snapshot. Child status updates do not enqueue mail. child-bridge.ts:66-81 index.ts:549-565 child_snapshot_manager.go:99-169

The Pi launch settings choose its model and provider. The router still owns its control and mailbox records in SQLite. This boundary follows from the launch arguments and the manager/store split. process.go:58-67 root_control_manager.go:100-152

03

Queue and persistence

Enqueue

A bounded ordinary queue

SQLite stores messages as queued. A repeated ID with the same envelope returns the existing row. Conflicting content fails. The store checks per-recipient message and byte limits and sets a one-hour expiry on new rows.

delivery.go:121-229
Ownership

Pick a delivery path when possible

After saving mail, the router looks up the recipient. An active source lets it save a fixed managed or tmux target. A reserved, missing, or conflicted source leaves the message without a fixed target; it normally waits in the queue (see the Web UI fallback). Later checks can fill in a missing target, but do not replace one already saved.

http.go:673-699
delivery.go:1131-1219
Delivery

Confirm delivery on each path

For tmux, the router records a time-limited agent lease and a delivery attempt, then waits for a WebSocket receipt. For router-started Pi, it records an attempt tied to the current process/session (a fence) and waits for Pi to confirm the transcript append over RPC. Both start with queued mail.

delivery.go:359-435
delivery.go:1236-1342

The store and Pi session file serve different purposes. SQLite owns routing and acknowledgment. The Pi transcript supplies evidence that a managed prompt was appended. rpc.go:2805-2841

Concrete journeys

Tmux to RPC

Supervisor sends mail to router-started Pi

For example, the supervisor sends a message addressed to the Pi agent. The router saves it. Once that recipient has an active managed source, the router records the direct delivery path. It records an attempt tied to the current Pi process and marks it prompted before writing the RPC command. Pi returns a transcript append receipt; the router then acknowledges the original message. RPC to tmux

Pi replies to the original sender

In that example, the supervisor is the original sender and Pi is the recipient. After Pi confirms the incoming message was appended and the direct turn settles, the router takes the final nonempty assistant text from that same turn. It queues a new mailbox message addressed back to the supervisor, with a stable reply ID. A tmux socket can claim and acknowledge that message. Ordinary streamed text is not mailed. Text outside this direct delivery is not intended as a reply. If Pi calls mecha_mailbox_send, that is a separate tool action: Pi chooses a recipient and can send another message.

Direct deliveries run one at a time for each Pi agent. The receipt identifies the incoming message, but assistant reply and settled events do not carry that message ID. If an old reply arrives after the next message’s receipt, the router could send it to the next sender. This is a risk in the code, not an observed failure; the documented tests do not cover it. supervisor.go:2444-2456, 2667-2685, 2803-2820 · rpc.go:2235-2289 · http.go:651-670

Restart

After a router restart

The router checks saved work before accepting normal traffic:

  1. Check router-started Pi agents and unfinished launches. A crash may have happened after Pi started but before the router saved the outcome.
  2. Resume interrupted restart, reset, or terminate operations. A saved request may still need process work or a final result.
  3. Repair the record of which agents can receive mail. Then assign a delivery path to queued messages that still have no target, if their recipient now has an active source. Already chosen targets stay fixed.
  4. Inspect unfinished direct attempts against Pi's transcript before retrying. An RPC write may have appended the message even if the router missed its receipt.

Periodic checks also handle expired queued messages and timed-out deliveries. Failures describes when proof from the old process or Pi transcript is needed.
