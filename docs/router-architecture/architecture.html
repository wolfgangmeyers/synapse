System / 01

Architecture

One router accepts messages for two worker lifecycles. SQLite records the queued message first. The router snapshots its delivery owner when the recipient has an active source; a missing source leaves the message queued.

“Managed worker” is ambiguous here. A browser-launched RPC Pi is router-owned. A supervisor-launched Pi in tmux is a separate worker, even when both appear in the same UI.

Current managed-control flow

The browser sends managed actions to the router’s HTTP API. Provider sign-in and sign-out use /v1/provider-auth and its action and prompt-response routes; the router records operations and passes interactions to the provider-auth coordinator. /v1/models reads the available catalog and saved default. /v1/settings/default-model saves a validated available model; launch and restart can specify a model. The manager selects the model for its Pi process. managed_http.go:33-117, 126-230, 231-385, 489-572, 663-714

Restart, reset, and terminate requests go through HTTP to the managed manager and its durable operations before process work. Goal reads and updates call a direct Pi root control through the manager; updates also record an operation. Inline-tool settings are read and updated through the manager, with update operations recorded in SQLite. The UI reads managed status through HTTP and the projection-only /v1/ui-live WebSocket. managed_http.go:83-115, 663-806, 1268-1410 ui_live.go:49-68

Managed HTTP controls are locally unauthenticated: anyone who can reach the router can invoke them. The router does not use cookies, sessions, CSRF tokens, or Origin as authorization. CORS is transport compatibility, not a security boundary. Keep router reachability limited to trusted clients. managed_http.go:37-43, 663-668 ui_live.go:49-68

Control request and result: An installed managed Pi tool emits a hidden control request over its RPC stdout. The manager validates and stores it, then invokes the local Python host. It stores the result and sends a hidden RPC command back to Pi. Pi appends the result to its session transcript; the manager checks the receipt before marking delivery. This is not a mailbox send unless the requested operation is mail.send. rpc-client.ts:21-35 rpc.go:541-568 root_control_manager.go:89-152, 405-418, 531-602 managed_root_control.py:546-555

Child telemetry: The fork exposes child lifecycle state to mecha-rpc. The extension emits hidden child deltas on Pi RPC; the manager applies them to the store and refreshes the UI projection. A missing sequence triggers a snapshot read. This path does not enqueue mail. child-bridge.ts:66-81 index.ts:549-565 child_snapshot_manager.go:99-169

Boundary inference: the selected provider and model govern Pi's model calls, not the router's control or mailbox storage. The launch arguments and manager/store split support this reading. process.go:58-67 root_control_manager.go:100-152

03

Queue and persistence

Enqueue

A bounded ordinary queue

SQLite stores messages as queued. A repeated ID with the same envelope returns the existing row. Conflicting content fails. The store checks per-recipient message and byte limits and sets a one-hour expiry on new rows.

delivery.go:121-229
Ownership

Recipient source snapshot

The router reads its durable recipient directory after enqueue. An active source yields a fixed managed or tmux target. Reserved, missing, and conflicted sources leave the message queued. Reconciliation fills snapshots that were missing, without changing existing ones.

http.go:673-699
delivery.go:1131-1219
Delivery

Two receipt protocols

Tmux delivery uses a durable agent lease, delivery attempts, and WebSocket receipts. Managed delivery creates a separate fenced direct attempt and waits for an RPC append receipt. Both start from an ordinary queued message.

delivery.go:359-435
delivery.go:1236-1342

The store and Pi session file serve different purposes. SQLite owns routing and acknowledgment. The Pi transcript supplies evidence that a managed prompt was appended. rpc.go:2805-2841
