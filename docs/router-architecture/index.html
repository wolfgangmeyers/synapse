Router architecture

The router saves messages and delivers them to agents. It can start a Pi agent itself, or deliver to a worker started by the supervisor. Those agents run and recover differently.

Fact means current code or a cited test supports the claim. Assessment means a conclusion or proposed next step. Older root RPC_*.html files describe research and plans, not current behavior.

A few names used in this guide

Router-started Pi (managed root)

The main Pi agent started by the router for a browser request. “Root” means the main agent, not a child agent. It runs without tmux, using RPC: commands and events exchanged with Pi over process pipes.

process.go:50-67 · child-bridge.ts:1-32

Supervisor-started tmux worker

An agent started in a tmux window by the supervisor launcher. It may also be Pi, but the router did not start or own its process.

worker_launch.py:803-858

Queue and delivery

The queue is the router’s saved list of messages in SQLite. An active source fixes the delivery path: a direct RPC prompt to router-started Pi, or a WebSocket delivery to a tmux worker. Without one, mail has no fixed target and normally waits in the queue. An eligible connected Web UI may receive it through a temporary in-memory lease; the UI does not become its persistent owner.

delivery.go:1131-1194, 345-397 · http.go:673-699 · websocket.go:1566-1580

Attempt, receipt, and fence

An attempt is one recorded try to deliver a message. A receipt confirms that Pi appended it to its transcript or that a tmux client acknowledged it. A fence ties work to the current agent process/session so an older process cannot finish a newer attempt.

supervisor.go:2670-2813 · delivery.go:359-435

Who starts the agent?

Fact / router-owned

Router starts the main Pi agent

A browser request to /v1/managed-agents makes the router reserve an agent in SQLite and start Pi in RPC mode. It is the managed root, not a Pi child. This path has no tmux window.

Launch sequence · process.go:50-67
Fact / supervisor-owned

Supervisor starts a tmux worker

The supervisor launcher creates a tmux window for Pi, Claude, Codex, or Cursor. Even when this worker is Pi, its process belongs to the supervisor launch path. The UI labels router-started agents RPC and other agents tmux.

Worker ownership · worker_launch.py:803-858 · AgentRow.tsx:45-67
02

How mail and control move

Fact / mail

One saved queue, two delivery paths

HTTP sends are saved in SQLite first. When the recipient has an active source, the router records which kind of agent will receive the message. Without one, the message has no fixed target and normally waits in the queue (see the Web UI fallback). A tmux worker claims mail over WebSocket. Router-started Pi gets a direct RPC prompt and sends a transcript append receipt.

Message map · Cross-path examples · delivery.go:1131-1155
Fact / control

The main Pi agent can request a tmux worker

Router-started Pi can call mecha_worker launch. The router checks that the request came from its current process, saves it, and asks a Python host to run the supervisor launch script. The tool first reports queued. A matching result arrives later.

Control sequence · root_control_manager.go:54-150

What needs attention

Assessment / recovery

A crash can interrupt delivery after Pi or tmux acted

SQLite cannot save a Pi transcript append or a tmux launch in the same transaction as its own records. Receipts, time-limited ownership (leases), process fences, and recovery checks help the router decide what happened. A timeout alone does not prove the action failed.

Ambiguous append · Complexity assessment · Uncertain launch result
Fact / test scope

Coverage crosses several boundaries

Behavioral tests cover HTTP launch, mixed HTTP and WebSocket mail, and controlled crash recovery. Native tests exercise installed Pi on selected paths. The documented tests do not join a Pi root tool call to a real tmux launch and delivered result.

Assessment / future option

pi-go remains unresearched here

A Go runtime might simplify the subprocess boundary, but its API and compatibility have not been verified. Keep router contracts and test parity before considering a swap. The tmux path is separate.
