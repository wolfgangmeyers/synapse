Router architecture

One router carries mail between two kinds of worker. Their launch, delivery, and recovery paths differ.

Fact means current code or a cited test supports the claim. Assessment means a conclusion or proposed next step. Older root RPC_*.html files describe research and plans, not current behavior.

01

Which worker?

Fact / router-owned

Browser-launched Pi

The browser posts to /v1/managed-agents. The router reserves an agent in SQLite and starts Pi in RPC mode. This path has no tmux window.

Launch sequence · process.go:50-67
Fact / supervisor-owned

Tmux worker

The supervisor launcher creates a tmux window for Pi, Claude, Codex, or Cursor. Pi running here is still a tmux worker. The UI labels router-owned agents RPC and other agents tmux.

02

How mail and control move

Fact / mail

One queue, two delivery paths

HTTP sends enter the SQLite queue. The router pins a queued message when its recipient source is active. If the source is missing or inactive, the message stays queued without a target. Tmux workers claim mail over WebSocket. Router-owned Pi receives a direct RPC prompt and settles it with a transcript receipt.

Message map · Cross-path examples · delivery.go:1131-1155
Fact / control

A root tool can launch a tmux worker

A router-owned Pi root can request mecha_worker launch. The router admits a fenced request, and the Python host calls the supervisor lifecycle script. The tool first reports queued; a correlated result arrives later.

Control sequence · root_control_manager.go:54-150
03

What needs attention

Assessment / recovery

The risky gap is after an outside effect

SQLite cannot commit a Pi transcript append or tmux launch in the same transaction. Receipts, leases, process fences, and recovery checks protect those gaps. A timeout alone does not prove the effect failed.

Ambiguous append · Complexity assessment · Uncertain launch result
Fact / test scope

Coverage crosses several boundaries

Behavioral tests cover HTTP launch, mixed HTTP and WebSocket mail, and controlled crash recovery. Native tests exercise installed Pi on selected paths. The documented tests do not join a Pi root tool call to a real tmux launch and delivered result.

Test evidence · Proposed cross-boundary tests
Assessment / future option

pi-go remains unresearched here

A Go runtime might simplify the subprocess boundary, but its API and compatibility have not been verified. Keep router contracts and test parity before considering a swap. The tmux path is separate.
