Future option / not an implementation report

Could pi-go replace the Pi RPC runtime?

Maybe. This is a proposed migration seam, not a finding that pi-go already supports these contracts. The existing design starts a Pi RPC subprocess under the Go router.

The root documents research Pi RPC, not pi-go. Their installed-runtime evidence names Pi 0.85.0 and is historical. Local pi --version reports 0.87.1 on 2026-09-26. Validate against the runtime installed at migration time before making a replacement decision. RPC_RESEARCH.html:172-189 · RPC_IMPLEMENTATION_PLAN.html:13-28 · RPC_SPEC.html:307-328

The boundary today

These are current source observations. The root specification describes the intended system, not proof that every planned feature shipped.

The manager reserves a managed agent and Pi session, then starts a process. The process arguments include --mode rpc and fixed extension paths.

Router authority

Research limit

RPC is not a generic host API

Stock Pi RPC has no controller-defined callable tool registration, provider credential mutation, or authoritative child watch. The Pi extension and router bridge cover separate parts of that gap.

02

Contracts a replacement must keep

The requirements and specification set the target behavior. A different runtime would need equivalent behavior, even if its transport changes.

Identity and recovery

Stable managed agent

Keep durable identity, Pi-session continuity on restart, explicit context reset, crash bounds, and router-restart recovery. Keep the exact process/session fence until a tested replacement fence exists.

RPC_REQUIREMENTS.html:284-301 · RPC_SPEC.html:366-381 · supervisor.go:401-482
Tools and authority

Same behavior, guarded calls

Preserve the accepted manifest and tool names, strict schema validation, immutable definitions, sender identity derived by the router, and fenced control requests. Pi's local coding tools and child policy remain separate from router tools.

RPC_REQUIREMENTS.html:223-267, 312-333 · RPC_SPEC.html:329-357
Messages and UI

Same observable worker

Keep durable mailbox delivery and acknowledgment, cross-path messaging with tmux agents, complete and quiet histories, and structured parent/child snapshots with fenced deltas. Terminal text cannot establish child state.

RPC_REQUIREMENTS.html:302-321, 335-351 · RPC_RESEARCH.html:325-383

Proposal: write these as runtime-neutral conformance cases before changing production wiring. Treat a change to message order, persisted session format, or tool-result visibility as a contract change, not a transparent swap.

03

What could change, and what stays

Possible simplification

Remove a transport layer

Hypothesis: if pi-go offers an embeddable session with matching extension, tool, event, and persistence semantics, a Go adapter could avoid subprocess stdin/stdout framing and some process supervision. That capability has not been verified here.

Present subprocess boundary: process.go:61-63, 183-194 · RPC_SPEC.html:307-328
Still required

Router state and controls

Embedding a runtime would not remove SQLite records, idempotent operation admission, mailbox and history retention, sender authorization, lifecycle fencing, recovery policy, or browser projection. Those are router responsibilities.

RPC_SPEC.html:307-357 · router-proxy/internal/store/managed.go:676-704, 893-900 · managed_http.go:33-117
New risk

Shared failure domain

Inference: in-process execution could let runtime failure affect the router process. Process isolation currently gives the manager a separate child to stop. Compare failure containment, upgrades, and resource limits before accepting embedding.

process.go:183-194, 287-401 · RPC_SPEC.html:366-381
04

Small migration seam

Proposal: keep the router's HTTP surface, store, and policy handlers fixed. Introduce a runtime adapter behind managed-agent startup and event ingestion. Do not switch the tmux path.

  1. 01 / CharacterizeFreeze observable behavior

    Capture launch, tool control, mailbox, history, child state, restart, and reset cases against the current Pi RPC path.

  2. 02 / SpikeProve pi-go locally

    Use a deterministic fake provider. Verify tool schemas, event ordering, session persistence, auth boundary, and child events before production wiring.

  3. 03 / AdaptSwap one runtime boundary

    Keep router-owned admission and persistence. Map adapter events to existing fenced identities and receipts. Run only selected test agents on the new path.

  4. 04 / CompareGate wider use

    Test restart, router crash recovery, stale callbacks, duplicate delivery, and mixed tmux messaging. Roll back to RPC when parity fails.

Current seams: supervisor.go:361-482, 489-550 · process.go:61-63, 183-194. Steps above are proposals.
05

Proof gates and open questions

Gate / proposed

Runtime parity

Prove all required tool names and bounded schemas reach the model before its first turn. Exercise a real control request and later result. Check immediate versus delayed result semantics and canceled turns.

Contract: RPC_REQUIREMENTS.html:223-267, 312-333 · prior isolated proof limit: RPC_RESEARCH.html:269-285, 295-323
Gate / proposed

Recovery parity

Kill the runtime and router at each admission, append, and settlement boundary. Prove a restarted agent retains its session, stale generations cannot act, and duplicate requests do not repeat effects.

Contract: RPC_SPEC.html:366-381 · current operation lookup: managed.go:893-900
Gate / proposed

UI and mixed-mode parity

Check initial and reconnect snapshots, live parent and child transitions, mailbox exchange with tmux, and both histories. Keep existing RPC behavior available during comparison.

Contract: RPC_REQUIREMENTS.html:207-222, 302-321, 335-351 · evidence limit: RPC_RESEARCH.html:325-385

Questions before a decision

Which pi-go repository, version, and API are in scope? Does it read existing Pi session files? Can it run the fixed extension and subagent integration, or would those need replacement? Who owns credentials and model discovery? Can runtime failures be contained without taking down the router? None of these are established by the Pi RPC documents.
