Evidence / 04

Tests

Some tests check what the system does across several parts. Others start the installed Pi program. The first kind may use a stand-in for Pi; the second checks the actual Pi connection. Passing either kind does not prove the untested parts work together.

01

Behavioral coverage by flow

HTTP launch

Request to ready Pi

This test sends an HTTP request to start an agent. It checks the agent record in SQLite, then confirms the router marks the agent ready before sending its first instruction. Repeating the same request returns its saved response (replay). The router starts a real operating-system child process, but that process is a test program imitating Pi's JSON-RPC messages. It does not run installed Pi.

managed_launch_behavioral_functional_test.go:24-30, 37-118, 334-441
Root control

Router to Python host

This test runs the HTTP router, agent manager, SQLite store, and Python program that executes supervisor requests. It checks mail and reminder results, repeat requests, conflicting requests, and a second router used to test routing. Test replacements start the process and send Pi's RPC messages, so installed Pi never makes these supervisor requests.

domain1_behavioral_functional_test.go:19-23, 35-142, 160-248, 358-553
Native root

Installed Pi goal status

This test starts installed Pi with the real RPC extension. A fake model service gives a fixed goal status tool call during a normal agent turn. Pi receives a queued response while the router works. The router later marks the saved control-request row delivered after accepting a receipt that the result was added to Pi's conversation. That row does not prove a human saw it or a worker started. A reset cancels a request from the old session so it cannot act in the new one. Goal status runs inside the manager; this test does not start a tmux worker.

managed_root_control_native_test.go:351-505
Direct mail

Delivery and recovery

Tests that start installed Pi check direct mail delivery, an empty message, and recovery after an interruption. They test messages sent to Pi, but do not run the script that starts tmux workers.

managed_native_test.go:1026-1078
Supervisor tools

Adapter and dispatch

TypeScript tests check that mecha_worker launch selects the expected script and safe arguments. They replace the script runner with a fake. Python tests replace the subprocess too. They check replay (returning a saved result for the same request), reconciliation (looking up an earlier result after an interruption), and pruning (removing old saved results). If the saved result is missing, reconciliation returns an unknown-request error without running the script again. These tests do not start tmux.

operational_native_tools.test.ts:520-568
test_managed_root_control.py:21-117, 143-195
Other recovery

Crash and control receipts

Manager and RPC tests use fake processes and fake Pi messages to control exactly when a start, failure, or result happens. They check recovery and the rules for accepting result receipts. A valid receipt means Pi saved the result in its conversation. These fake-interface tests check that rule but cannot prove a real Pi saved it or that a tmux worker started.

crash_recovery_behavioral_functional_test.go:15-84
rpc_test.go:1358, 1464, 2715-2790
02

Coverage limits and useful next tests

The following tests are proposals, not passing test results. They would connect paths that the tests cited above exercise separately. Other end-to-end tests may already exist.

Proposal 01

Root tool to real tmux launch

Proposed test: have a fake model service tell installed Pi to call mecha_worker launch. Use the real router, Python supervisor-request program, saved supervisor state, worker-start script, tmux, and mail connection. Check that Pi first sees a queued response, exactly one tmux worker starts, Pi's control result is recorded as delivered, and the worker receives its instruction. Current installed-Pi coverage calls manager-owned goal status. The combined Python test uses fake process-start and Pi-message interfaces.

managed_root_control_native_test.go:414-461
domain1_behavioral_functional_test.go:160-173, 358-389
worker_lifecycle.py:91-133
Proposal 02

Crash between tmux start and host save

Proposed crash test: let worker_launch.py start a tmux window, then stop the Python supervisor-request program before it saves the result in requests.json. On restart, look up the old request without running it again (reconciliation). Expect ROOT_OPERATION_UNKNOWN: the program cannot prove whether the launch succeeded. Check that the one window survives and no second worker starts. The existing fake subprocess test cannot prove this.

managed_root_control.py:602-641
test_managed_root_control.py:69-93, 112-143
Proposal 03

Lost result receipt after worker start

Proposed crash test: start one real tmux worker and save the Python program's result. Stop the router or Pi before the router saves Pi's receipt for adding that result to the conversation. After reconnecting, check that there is still one worker, one saved control result, and one copy of that result in Pi's conversation. Existing code can look for the missing receipt in Pi's saved conversation. The combined router test uses a fake Pi receipt, so it does not prove this real crash case.

root_control_manager.go:539-622
domain1_behavioral_functional_test.go:80-142, 431-449

For these proposed tests, use a fake model service with fixed replies. Run the real router, Pi, and worker-start path together where the claim depends on them.
