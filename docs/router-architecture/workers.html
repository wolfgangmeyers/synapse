Lifecycle / 02

Workers

There are two ways to start a main agent here. The router starts Pi directly as a managed root (the main Pi agent, not one of its child agents). Or the supervisor starts a terminal worker in a tmux window. Tmux keeps that terminal process running and lets the supervisor reconnect. A terminal worker can also run Pi, but the supervisor still owns its launch.

Pi child agents are tasks started inside a main Pi session. They are neither a new managed root nor a supervisor-launched terminal worker. “RPC” means the router sends commands to its Pi process over input/output pipes. Mail goes through the router's message queue; control runs a requested action and reports its result. process.go:50-73 worker_launch.py:803-858 child-bridge.ts:1-32

02

Sequence: direct browser launch

The browser's request ID (X-Request-ID) identifies one HTTP launch request so a repeat can return the same response. The returned operation ID identifies that saved launch request. HTTP 202 means the router accepted and saved it. “Launched” means the Pi process actually started. “Ready” means this particular Pi process and session passed the router's readiness checks. These are different moments. managed_http.go:489-567 supervisor.go:541-770

  1. Browser → HTTPRequest

    Send POST /v1/managed-agents with name, working directory, optional model and initial instruction, and X-Request-ID.

    managed_http.go:489-538
  2. HTTP → storeAccepted

    Validate inputs and save the agent and launch request. Return 202 with the launch operation ID and an agent marked starting. Repeating that HTTP request ID with the same body replays the saved response, even if startup subsequently fails.

    managed_http.go:539-567
    supervisor.go:431-491
  3. Manager → PiStart and bind

    Start Pi, open the command pipe (RPC), and check that Pi reports the reserved session ID. Check this process's readiness before accepting its tool actions.

    supervisor.go:541-640, 708-755
  4. Pi → storeReady

    Save that this Pi session is ready, then send the initial instruction if present. If Pi exits later, its recovery is tracked separately.

03

Sequence: mecha_worker launch from an RPC root

Here a managed root asks the supervisor to start a terminal worker. Its tool first says queued: the request is queued locally for sending. The router may not have admitted it, and the worker may not exist yet. The result arrives later in that root's Pi conversation. This route never starts another managed root.

  1. Pi tool → routerQueued

    The Pi extension returns a control request ID and status: queued. That ID ties the tool call, saved action, and eventual result together. It starts sending the request privately to the router, but sending can fail later. This response proves neither router admission nor a terminal worker launch.

    tool-registry.ts:65-72
    rpc.go:86-98
  2. Router → storeAdmitted

    Once this managed root is ready, the manager checks the tool arguments and the runtime's identity. Its manifest is the list and definitions of tools allowed in this Pi process; the checks reject actions from a replaced process or changed tool list (a “fence”). SQLite saves the control request and an ID for its future result. A repeated request ID refers to the saved request.

    root_control_manager.go:54-150
  3. Host → tmuxEffect

    The local Python host calls worker_lifecycle.py launch --alias …. That script checks the supervisor's worker record and existing window, then runs worker_launch.py in the recorded checkout. The host saves the launch result under the control request ID.

    managed_root_control.py:519-526, 602-634
    worker_lifecycle.py:91-133
  4. Router → PiResult and receipt

    The router saves the host's result in SQLite. It then appends (adds) a private result message to this managed root's Pi conversation. Pi's append receipt identifies that conversation entry. The router marks result delivery only after saving that receipt and checking it belongs to the current session. The receipt proves the result reached Pi, not that the requested worker launched. An error result is tied to the same control request; it does not authorize another launch.

    root_control_manager.go:357-406, 507-623
04

When the result is uncertain

Host crash after launch

The terminal worker can start before the Python host saves its result. After a host crash, a missing saved host result produces ROOT_OPERATION_UNKNOWN; this means the outcome is unknown, not that launch failed or the worker is absent. Recovery does not run the launch again. Check the supervisor's worker record, tmux window, and router's saved control request before considering a new request.

managed_root_control.py:602-641
worker_lifecycle.py:96-101, 117-130

Timeout is not a rollback

The host command waits up to 30 seconds; its lifecycle subprocess waits up to 25 seconds. The router's control callback has a 45-second deadline. Reaching any deadline stops waiting, not necessarily the external work. It does not roll back an opened tmux window. After a restart, the manager checks the saved control request and host result before reporting an outcome.

managed_root_control.py:140-145, 626-632
worker_lifecycle.py:30, 55-72
root_control_manager.go:69-77, 197-254

Append ambiguity

SQLite can hold the host's action result while the receipt for adding that result to Pi's conversation is still missing. The router treats result delivery as uncertain and looks for that exact conversation entry. It marks delivery only after saving the matching Pi receipt. A missing lookup by itself cannot prove Pi never received the result.

root_control_manager.go:539-622

Inference from these paths: root tool queued means local enqueue for sending; router admission happens later. HTTP 202 means the router saved a browser launch request. Host success concerns the requested action. Pi readiness concerns one running managed root. A saved Pi receipt concerns one result message in that root's conversation. Check the terminal worker separately before calling it running.
