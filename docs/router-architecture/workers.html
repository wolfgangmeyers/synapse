Workers

A supervisor tmux worker and a router-owned Pi root are separate processes with separate owners. A Pi tmux worker is still a tmux worker.

01

Who owns each worker

Supervisor-owned

Tmux worker

worker_lifecycle.py resolves an active worker alias in supervisor state. It starts worker_launch.py, which opens a tmux window in the recorded worktree. The runtime can be Pi, Claude, Codex, or Cursor. The tmux window is the worker identity.

Router-owned

RPC Pi root

POST /v1/managed-agents reserves a managed agent and launch operation in SQLite. The router starts Pi with --mode rpc and a restricted extension set. No tmux window starts on this path.

Control and mailbox

A root tool request is a fenced control operation with a later result in Pi's transcript. ops.worker send invokes the mailbox sender. Mailbox delivery gives the tmux worker its instruction; it does not launch that worker. ops.worker launch runs the supervisor lifecycle script.

02

Sequence: direct browser launch

Acceptance is a durable reservation, not proof that Pi is ready.

  1. Browser → HTTPRequest

    Send POST /v1/managed-agents with name, working directory, optional model and initial instruction, and X-Request-ID.

    managed_http.go:489-538
  2. HTTP → storeAccepted

    Validate inputs and reserve the agent and operation. Return 202 with the operation ID and starting agent. Repeating the same request ID and body replays the stored response.

    managed_http.go:539-567
    supervisor.go:431-491
  3. Manager → PiStart and bind

    Start the process group, open RPC, and match Pi's session ID to the reserved session. Run readiness before enabling control intake.

    supervisor.go:541-640, 708-755
  4. Pi → storeReady

    Persist readiness, then submit the initial instruction if present. A later process exit has its own recovery state.

    supervisor.go:708-770
    managed_launch_behavioral_functional_test.go:382-475
03

Sequence: mecha_worker launch from an RPC root

The root's tool response says queued. The tmux launch result arrives later. This route does not create another router-owned Pi.

  1. Pi tool → routerQueued

    The extension returns a request ID and status: queued. It emits a hidden root-control request. This is not a success receipt.

    tool-registry.ts:65-72
    rpc.go:86-98
  2. Router → storeAdmitted

    After readiness, the manager checks runtime and manifest fences, validates arguments, and reserves a durable control request and result ID. A duplicate request reuses its existing row.

    root_control_manager.go:54-150
  3. Host → tmuxEffect

    The Python adapter calls worker_lifecycle.py launch --alias …. That script checks supervisor state and existing identity, then runs worker_launch.py in the recorded worktree. The host records its result under the control request ID.

    managed_root_control.py:519-526, 602-634
    worker_lifecycle.py:91-133
  4. Router → PiResult and receipt

    The router commits the result, appends a hidden control-result message to Pi, then marks delivery when the fenced append receipt is durable. A tool error is a correlated terminal result, not an instruction to repeat the effect.

    root_control_manager.go:357-406, 507-623
04

When the result is uncertain

Host crash after launch

The tmux launcher can complete before Python saves the host result. On recovery, an absent host record returns ROOT_OPERATION_UNKNOWN. It does not rerun the launch. Inspect supervisor state, tmux identity, and router control history before retrying with a new request.

managed_root_control.py:602-641
worker_lifecycle.py:96-101, 117-130

Timeout is not a rollback

The host script has a 30-second command timeout. The lifecycle wrapper has a 25-second subprocess timeout. Either timeout can leave the outside effect uncertain. The root manager's control callback has a 45-second context and reconciles recorded work after a restart.

managed_root_control.py:140-145, 626-632
worker_lifecycle.py:30, 55-72
root_control_manager.go:69-77, 197-254

Append ambiguity

A stored result can exist before Pi's append receipt reaches SQLite. The router marks submission as uncertain and reconciles against Pi's transcript. It acknowledges direct-turn settlement only after storing the matching receipt.

root_control_manager.go:539-622

Interpretation: queued, HTTP 202, host success, Pi ready, and a delivered result prove different boundaries. None alone proves the whole chain.
