Recovery / 04

Failure paths

A queued message can outlive a connection or process. Recovery depends on who owned delivery and how far the send got.

“Fact” below means the behavior is present in current code or the cited test. “Inference” describes a consequence of those paths. “Proposal” is a possible change, not current behavior.

01

Crash and restart

Recovery runs before ready

The router opens SQLite and builds the managed manager before listening. Managed startup exposes health while other requests return 503 router_starting. It then recovers roots, pending launches, restart transitions, lifecycle controls, recipient sources, message targets, and direct attempts before reporting ready.

04

Where the complexity comes from

Fact

Two delivery state machines share one queue

The store has legacy delivery attempts and managed direct attempts. Both depend on an ordinary message, but they settle through different receipts. Recipient snapshots prevent a queued message from switching owner when that owner restarts.

delivery.go:359-435
delivery.go:1131-1219

Inference

The hard boundary is external persistence

The router can commit SQLite state, but it cannot atomically commit a Pi session append in the same transaction. The prompted marker and transcript scan bridge that gap. This explains the extra recovery state. It does not prove every current state is necessary.

supervisor.go:2683-2708
rpc.go:2805-2841
Inference

Ownership needs more than a name

Leases fence tmux sockets. Managed attempts carry a Pi session, epoch, process identity, runtime generation, and manifest. A recipient name alone cannot distinguish a restarted process from the one that wrote the original prompt.

05

Other recovery boundaries

Mail receipts are one part of the complexity assessment. These paths have different owners and failure points.

Fact / host result ledger

The host records root operations

The Python runner locks a local request file, checks the request ID against its input fingerprint, and saves the result before returning it. Reconcile reads that record; an unknown ID returns an error. Records are pruned by age and count. The host owns this file, outside the router store.

Inference: A host action can finish before its result is recorded. The file cannot prove what happened in that window. Proposal: Keep the request-ID fence for external actions. Audit whether any duplicated result fields can be derived from the host record while it remains retained.

managed_root_control.py:104-153
managed_root_control.py:602-641
Fact / root result append

The router owns delivery into Pi

The Go manager claims a stored result append with an owner and runtime fence, checks the payload hash, submits it to Pi, and marks submission uncertain before using the live receipt. If that receipt is lost, it reconciles against Pi using request, result, payload, and runtime identity.

Inference: The host's saved result cannot prove Pi appended it. Proposal: Keep the append owner, uncertainty marker, and Pi receipt check. Review overlapping result/status copies only where the same durable record can supply them.

root_control_manager.go:532-627
Fact / child repair

The manager repairs missing deltas from Pi

A bounded per-binding queue drains child deltas in order. On overflow it replaces a waiting item, leaving a sequence gap. The store applies fenced deltas; gaps or conflicts trigger a fresh Pi snapshot. A matching owner and live binding are checked before the store accepts repair.

Inference: A missing delta can make a child view wrong until snapshot repair succeeds. Proposal: Keep the sequence and owner checks. The waiting queue is a candidate for simplification only if the durable snapshot repair still covers dropped updates.

child_snapshot_manager.go:34-120
child_snapshot_manager.go:155-197
Fact / live UI projection

The store owns the view; the hub sends it

UI subscription samples the stored projection while publication is locked, sends initial agent and child snapshots, then registers the browser. Later publications read the store again; missed versions get a full snapshot. The hub keeps a current in-memory copy for comparison.

Inference: Publishing between snapshot and subscription would lose an update without that ordering. Proposal: Treat the hub copy as disposable comparison state. Keep the store read and ordered subscribe handoff if the projection code is reduced.

06

Possible simplifications

These are proposals for investigation. None is a claim about the current implementation.

Proposal

Draw one transition table

List each message state, owner, receipt, retry rule, and terminal outcome side by side for tmux and RPC. Use it to remove duplicated bookkeeping only after crash-boundary tests cover the same contract.

Proposal

Keep one routing decision

Keep the immutable recipient snapshot as the boundary between queue and delivery. Audit older fallback paths against it. Consolidate only paths that preserve queued messages when a source is reserved or conflicted.
