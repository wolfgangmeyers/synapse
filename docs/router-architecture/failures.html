Recovery / 04

Failure paths

Two kinds of main agent can receive mail. The router starts Pi directly as a managed root (its main agent). The supervisor starts a terminal worker in a tmux window, which keeps its terminal process running and reconnectable. That worker can also run Pi. Child agents run inside a main Pi session; they are not either kind of main-agent launch. A queued message can survive either process restarting.

RPC means commands exchanged with the router-started Pi over process pipes. The router's control requests ask for actions such as launching a terminal worker; mail is a message delivered to an agent. “Fact” means current code or a cited test. “Inference” follows from those paths. “Proposal” names a change to investigate. process.go:50-73 worker_launch.py:803-858 child-bridge.ts:1-32

01

Crash and restart

Fact / router startup

The router checks saved work before serving it

At startup, the router opens SQLite and prepares its manager for router-started Pi agents. It begins listening while it checks saved state. The health endpoint answers during this check: health means the HTTP listener responds, not that agents or mail are ready. Other requests get 503 router_starting until the startup pass finishes. That pass checks which managed roots should still run, closes incomplete launch records, settles unfinished restart and stop actions, checks which kind of agent owns each mailbox address, fills missing message destinations, and revisits in-progress delivery to managed Pi. Only then does router readiness change to ok.

Fact / managed roots

Restarting Pi is conditional

The manager looks at the saved request to keep each root running, the old process identity, whether an orderly stop was recorded, and any crash retry deadline. It resumes eligible roots. A launch still pending when the router stopped gets a separate path that records an unsuccessful end for that incomplete launch. Periodic checks retry eligible root recovery and time-limited mail deliveries. Router readiness means this startup pass completed, not that every Pi root is already usable.

02

Who can receive and acknowledge mail

Fact / tmux

A terminal worker holds the right to receive

When a terminal worker registers its WebSocket connection, the router saves that its mailbox address belongs to this worker type and grants a lease: a temporary, saved claim by one live instance. Another live instance using the same name is rejected. Receiving a queued message records a delivery attempt. The router accepts the worker's injection and acknowledgment messages only when its WebSocket session and lease still match.

Fact / retries

Timed-out mail is checked again

A periodic check finds expired queued messages and timed-out delivery attempts. It records timeout or dead-letter events (dead-letter means delivery ended without success), then offers any still-eligible message again. Timeout does not undo an earlier Pi conversation append. The terminal worker checks its Pi session before acknowledging mail that might already be in its conversation.

Fact / source

Each message keeps its chosen destination

Once the recipient is active, the router saves a target snapshot: a copy of whether this queued message belongs to a managed root or terminal worker. If nobody is active, the message stays queued. An existing choice remains fixed when ownership changes. Startup fills missing choices where it can; a missing destination lookup alone does not prove the recipient is absent. Sending directly to a managed root requires its active source and matching process, Pi session, runtime generation (generated runtime identity), and readiness identity. These identity checks are a fence: they reject an old process's work.

03

The ambiguous append

Here “append” means adding a mail instruction to the managed root's Pi conversation. Pi can save that entry before the router saves its acknowledgment in SQLite. A second send could add it twice. A Pi conversation receipt proves the entry was saved there; a router-accepted mail request only proves the router queued it.

  1. Fact / 01Reserve

    SQLite records one attempt to deliver the message to the managed root chosen by that message's fixed destination. It also saves the identity of the running Pi process allowed to receive it.

    delivery.go:1236-1308
  2. Fact / 02Mark before write

    Before sending Pi the mail instruction through RPC, the manager saves direct_prompted and a key for finding this exact message in that Pi session later.

    supervisor.go:2683-2721
  3. Fact / 03Wait for receipt

    Pi returns a receipt for the conversation entry. Once SQLite saves it, the router can acknowledge the original queued mail. If the router stops between those steps, the attempt still needs checking.

    supervisor.go:2753-2813
    delivery.go:1360-1431
  4. Fact / 04Reconcile

    Recovery asks that managed root's Pi session for a receipt matching this mail attempt. A match acknowledges the queued message without sending it again. The current code releases the attempt for retry if its lookup returns no receipt, and also after a lookup error. That release is a code path, not proof that Pi never received the mail; a failed or incomplete lookup leaves the outcome uncertain.

    supervisor.go:2892-2979
    rpc.go:2805-2841

Test boundary: the append/ack test interrupts the router's acknowledgment, starts competing recovery checks, and verifies that a matched Pi receipt settles the original mail without a second instruction. Its Pi RPC is a controlled fake. It tests the manager and SQLite interaction, not every stock Pi conversation behavior. managed_delivery_append_ack_native_test.go:90-274

Inference / untested risk: Managed mail instructions run one at a time, and the router saves which sender owns the instruction. Pi's assistant message_end and agent_settled events do not carry that incoming message's ID. If a late assistant event from the previous turn arrives after the next message's append receipt, the router could attribute the reply or settlement to the wrong sender. This has not been observed. The cited reply test checks one turn, not late events interleaved across two turns. Test that ordering with distinct senders before treating reply attribution as guaranteed. rpc.go:2235-2289 supervisor.go:2667-2685, 2803-2820 rpc_test.go:1251-1285

Where the complexity comes from

Fact

One queue, two ways to deliver

SQLite stores an ordinary queued message. A terminal worker uses a WebSocket delivery attempt and its own acknowledgment. A managed root uses a direct Pi delivery attempt and a receipt for its Pi conversation entry. The saved destination on each message keeps it with the chosen worker type across a restart.

Inference

SQLite and Pi save separately

A SQLite transaction commits several database changes together or rejects them together. It cannot include the separate write to Pi's conversation. The router saves “about to send” before the write and checks Pi's conversation afterward. That explains extra recovery records, though it doesn't establish that every record is needed.

supervisor.go:2683-2708
rpc.go:2805-2841
Inference

Names survive process replacement

A terminal worker's lease identifies the worker instance authorized to receive mail. Conversation-sync WebSocket connections can share that lease. A managed mail attempt also names the Pi session, session epoch (the session's saved incarnation number), process, runtime generation, and manifest (the selected tool definitions for that Pi runtime). These checks reject an acknowledgment from a replaced process. The recipient name by itself remains the same across restarts.

05

Other recovery boundaries

Other saved results have different owners. A receipt for mail appended to Pi's conversation says nothing about a terminal worker launch. Each path needs its own check.

Fact / host result ledger

The host saves an action result

The Python host locks its local request file, checks that the control request ID has the same inputs as before, and saves the action result before returning it. That file is a host ledger: a local list of saved request IDs and results, separate from router SQLite. Recovery reads that saved result. An unknown ID returns ROOT_OPERATION_UNKNOWN, not proof that the action did nothing. The file drops old entries by age and count.

Inference: The terminal worker might start before the host saves the launch result. A timeout does not undo that launch. Proposal: Keep the request-ID check before repeating external actions. Audit duplicated fields only while the host's saved result remains available.

managed_root_control.py:104-153
managed_root_control.py:602-641
Fact / root result append

The router delivers that result to Pi

The Go manager saves who owns this attempt to add the host result to the managed root's Pi conversation. It checks the result content and current process identity, then sends it to Pi. It marks the submission uncertain before acting on Pi's receipt. If the live receipt is lost, it looks up the conversation entry by control request ID, result ID, content hash, and process identity.

Inference: A saved host result does not prove Pi received it. Pi's result-entry receipt proves the append, not the worker launch. Proposal: Keep the saved attempt owner, uncertain state, and exact Pi receipt check. Review duplicated result fields only when the surviving saved record supplies them.

root_control_manager.go:532-627
Fact / child repair

The manager repairs child-agent status

Pi sends a delta (one child-agent status change) for each update. A bounded waiting queue for that managed root processes them in order. If full, it replaces a waiting update. Missing sequence numbers or conflicting updates make the manager request a snapshot: Pi's full current child-agent status list. SQLite accepts that repair only from the same live parent Pi session.

Inference: The displayed child status can lag until snapshot repair succeeds. Proposal: Keep the ordering and session checks. Simplify the waiting queue only if the full snapshot still repairs dropped changes.

child_snapshot_manager.go:34-120
child_snapshot_manager.go:155-197
Fact / live UI projection

The browser gets a current status view

A projection is the browser-facing status view built from SQLite. While new publications are paused, the router reads the saved agent and child status, sends full snapshots (copies of those lists) to a newly connected browser, then registers it for updates. Later updates reread SQLite. If versions were missed, the browser gets full lists again. The live hub also holds a copy in memory for comparison.

Inference: An update between the first snapshot and subscription could be missed without that ordering. Proposal: Keep the ordered read and subscription if the status view is simplified. Treat the hub's copy as replaceable comparison state.

Possible simplifications

These are proposals for investigation. None is a claim about the current implementation.

Proposal

Draw one transition table

List each queued message's state, current delivery owner, acknowledgment evidence, retry rule, and final outcome for terminal workers and managed roots. Remove duplicated records only after tests cover crashes between each saved step.

Current transitions: delivery.go:359-465, 1236-1460
Proposal

Keep one routing decision

Keep each message's fixed chosen destination between queuing and delivery. Check older fallback routes against it. Preserve queued mail when ownership is still reserved or disputed.

Current snapshot: delivery.go:1131-1219
Proposal

Test the real transcript seam

Test stock Pi across a crash between writing mail into its conversation, recording Pi's entry receipt, and committing the router's acknowledgment. Exercise HTTP and WebSocket too. Controlled fake RPC tests alone cannot establish what stock Pi saves.
