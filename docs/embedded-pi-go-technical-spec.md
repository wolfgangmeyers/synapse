# Embedded Pi Go: technical specification

## Decision and boundary

Run a router-managed root and router-launched managed workers as **independent in-process Go sessions**. Each has its own persistent agent ID, mailbox, session/epoch, model, run generation, controls, and lifecycle. A worker is not a Pi child and is not a tmux window. Both use the same router queue, SQLite control records, managed HTTP routes, and live UI. Keep the existing RPC root and supervisor-owned tmux/WebSocket workers unchanged as rollback and mixed-mail paths. No recursive/native subagents in v1. No import of old Pi sessions, automatic tmux migration, TypeScript extension execution in Go, or speculative cross-runtime compatibility layer.

Only Codex OAuth and Codex Responses are in scope. No Google, Cursor, or generic API-key parity. An embedded runtime is opt-in per **new** root/worker. An existing RPC session remains RPC across restart; rollback does not reinterpret its transcript as a Go session. Do not call the replacement ready until all gates below pass.

## Durable state and receipts

1. **Acceptance:** `/v1/messages` validates and commits a message ID, envelope, fixed destination when known, limits, expiry, and queued status in SQLite. Its success/acceptance ACK means *only* SQLite accepted mail. It does **not** wait for a conversation append, delivery, model turn, or reply. Duplicate ID plus identical envelope replays; conflicting content fails. Preserve the existing distinction for HTTP `202` launch: saved operation, not ready agent.
2. **Delivery:** Serialize direct delivery per agent. SQLite reserves a specific attempt with agent ID, session ID/epoch, run generation, message ID, and immutable append key before touching the session. Append the exact mail entry once to the intended ordered conversation, with checked write/flush/sync and a stable key; make the entry recoverably visible to that session. Only then commit the **processing/delivery ACK** for that exact attempt in SQLite. Conversation entry ID or `Run` success alone is not an ACK. If that final commit fails, keep the attempt pending for reconciliation. Normal inbound UI prompts and control-result messages need the same durable conversation boundary before claiming they were delivered.
3. **Conversation authority:** Keep one ordered durable journal per session/epoch (a checked Go recorder replacement or equivalently durable transaction), including user, assistant, tool call/result, mail attribution, model change, and compaction checkpoint. Store its identity/path and last validated sequence/branch in router state; the journal is context evidence, **not** an accepted-mail/ACK ledger. On reopen, verify complete ordered entries, parent/sequence continuity, session binding, and checkpoint position. Corrupt or missing entries block resume and delivery instead of silently skipping lines or starting a new conversation. Persist before reporting transcript append success. A first prompt must survive a crash before assistant output. Never claim that SQLite and a separate journal commit atomically.
4. **Reconcile:** On restart, compare the SQLite attempt to the durable entry by session/epoch + message/attempt/key + content digest. Exact match: commit missing ACK without a second append. Proven never attempted: permit a new delivery attempt. Unreadable, partial, conflicting, or possibly appended evidence: mark delivery **uncertain** and stop automatic retry until resolved. This is deliberately stricter than treating a negative lookup as proof of absence. SQLite stays the only authoritative accepted-mail/ACK ledger. An interrupted external tool effect is independently uncertain even if its conversational result is absent; never blindly replay it.
5. **Reply:** Bind final assistant output and settled status to the initiating turn ID and its original sender; ignore late events from another turn/generation. Queue one stable-ID auto-reply only after that turn settles and the result is durable. Streamed fragments are not replies. `mecha_mailbox_send` is a separately validated, correlated SQLite enqueue, never folded into auto-reply.

The historical [`embedded-pi-go-i4m2-gate.md`](embedded-pi-go-i4m2-gate.md) showed a returned recorder entry ID before any file existed and silent create failure despite `Run`/`Close` success. This **does not block SQLite mail acceptance**. It does block claims of durable ordered conversation recovery and delivery ACK proof until the new append seam is tested. The historical report's transcript-as-acceptance-receipt reading is superseded by the two ACK boundaries above.

## Lifecycle, tools, and status

- **Launch:** Reserve root/worker ID, canonical request hash, operation ID, requested model, cwd, session/epoch, and desired state in SQLite before constructing a session. Same `X-Request-ID` and body returns saved result; mismatch conflicts. One worker-launch control request maps to one durable worker record and unique identity, even if the router crashes after construction but before result delivery. On recovery inspect the record and generation before starting anything; unknown external completion is reported unknown, not re-executed. Enforce bounded agent count, pending work, turn queue, and per-turn deadlines. Worker list/send/cancel/cleanup/result operations use this independent identity and mailbox; parent relationship is metadata, not ownership of the worker's session. Parent restart/reset must not implicitly duplicate workers.
- **Start/restart/reset/terminate:** Restore desired agents after SQLite and journal reconciliation, then mark each ready only after model/auth, tools, history and checkpoint bind. Keep saved launch/restart/reset/terminate outcomes, bounded retry/backoff, and old-run fences. Health may answer while recovery is running; normal managed traffic remains gated until startup repair, and an individual agent can remain not ready. Restart continues the same ordered session/epoch; reset cancels and fences pending callbacks, creates a **new** session/epoch, and does not inherit old conversation/compaction or re-inject mail from the old epoch. Terminate fences the run and stops new turns. Explicit cancellation/timeout never implies a completed external effect was rolled back.
- **17-tool requirement:** Preserve the current managed manifest's 17 effective tool names: revision-one `pi-extensions/mecha-rpc/manifest.ts` defines 16 (`goal`, `goal_snooze`, `mecha_parent_message`, `mecha_mailbox_send`, `mecha_request_inline_tool_allowance`, `mecha_recall`, `mecha_settled_notifications`, `mecha_context`, `mecha_state`, `mecha_priority`, `mecha_verification_handoff`, `mecha_reminder`, `mecha_worker`, `mecha_pr`, `mecha_git`, `mecha_router`); checked-in revision-two `router/contract/managed-tools-v1.json` adds `web_search__4f4ca2a3ae8ea237531b8c5264d53d15474c0848fc8d7eeada0fef5b85b139ac` (`web.search`). The router's `internal/managed/manifest.go` and `root_control_handlers.go` validate this seventeenth operation. Gate 1 must verify the exact effective schemas and actions against that pinned contract, including search dispatch; no phantom missing tool or additional dynamic installs. Install only this fixed host allowlist and separately approved built-in read/bash/edit/write permissions before the first model request, validate per-action inputs and caller fence on the host, and reject runtime-added executable tools. The current TypeScript supplemental-install mechanism is not a Go dynamic-tool requirement. `queued` from a tool is local submission only; router admission, saved host result, durable result append, and effect success are distinct states. Saved requests/results must be correlated and idempotent. Reconcile worker state on interrupted launch; unknown effects stay visibly unknown.
- **Policy/features:** Preserve goal status/set/off, snooze limits/budget/refill and evaluator wakeups, reminders and verification handoff, inline-tool allowance, recall and settled notifications, `mecha_context` manual/automatic compaction and post-compaction handoff. Persist the actual compaction checkpoint before projecting success; preserve context/history order after restart. Support full transcript and bounded quiet/complete history as separate views. Indicators (turn, tool, compaction, goal/snooze, worker, auth/model) come from current fenced session events plus durable router state. Publish a fresh authoritative snapshot on reconnect and ordered versioned deltas; drop late generation events, repair gaps from snapshot, never infer a worker or completion from streamed text. Do not show ready if auth, journal, or checkpoint cannot reopen.
- **In-process failure domain:** Recover panics at each agent/turn/tool boundary and record agent failure without crashing a healthy router where possible; process-wide faults still take down the router. Bound concurrency, memory pressure, output size, tool execution, and provider streams. Apply context cancellation; quarantine blocked/uncooperative calls and refuse a replacement turn until the old effect is resolved. Startup must treat an unclean process exit as possible interruption, not proof of safe retry. No claim of OS-level isolation.

## Codex login, model selection, and security

The router already owns provider-auth operations and their non-secret status projection for the RPC path. Implement Codex-only embedded login/prompt-response/logout through the existing `/v1/provider-auth` route family; do not assume the current helper is an embedded Go OAuth integration. Complete authorization with bounded state/PKCE and prompt lifetime, validate callback/response binding, cancel cleanly, and never publish codes or tokens. The requirements exclude secrets from SQLite and browser status. For the embedded path, choose owner-only protected durable credential storage outside SQLite and serialize refresh and login/logout per provider; this storage layout is a proposed implementation, not an existing Go integration. Write rotated secrets atomically (temporary file, sync, rename, parent sync), and commit before use/publication so a restart cannot resurrect a spent refresh token. Failed refresh leaves auth unavailable with a safe status; never print tokens in logs, UI, history, errors, or tool output. Codex Responses streaming must carry tool-call IDs/arguments and final outcomes correctly, honor cancellation/retry policy, and use refreshed OAuth credentials for each request without leaking them.

`GET /v1/models` and provider status expose only Codex OAuth-filtered **available** chat models with an auth revision. The router model catalog/selector (`internal/managed/models.go`) owns validation and persistent default/agent selection; no unconditional hardcoded fallback to an unauthorized or stale model in the embedded path. Reject unavailable, stale, signed-out, or wrong-provider selections at launch, default update, active change, and restart. Persist selected provider/model and project it through managed HTTP and UI-live. For an idle agent, switch before its next turn. For an active agent, serialize the change at a turn boundary (or explicitly cancel and fence the old turn); atomically record the operation and selected model only after the live session confirms the new selection. On restart revalidate against refreshed OAuth-filtered catalog and keep the agent not ready if its saved selection is unavailable rather than silently substituting one. Test refresh, login/logout, revision races, active/idle changes, and restart using the real provider request boundary, not only catalog rows.

Keep working-directory/project trust, tool permissions, command/path restrictions and manifest bounds at least as restrictive as the current managed runtime. Existing managed HTTP controls have no authentication (`router-architecture/architecture.html`): CORS/Origin is not authorization. Limit listener/network access to trusted clients, do not broaden exposure, and treat root/worker IDs and UI status as non-secret but not authority. No caller-chosen tool list or model provider bypass.

## Implementation gates and verification plan

These are required **future** gates, not tests performed by this document.

1. **Freeze contract/build:** verify the source-backed 16 baseline plus revision-two web search against exact effective actions/schemas, approved built-ins, Codex model/filter policy and worker identity/UI shape. Pin SDK commit and reproducibly build router with Go 1.26. Confirm no old-session migration or new worker tmux launch is needed.
2. **Prove journal seam first:** fake model, real Pi Go session and durable journal; crash before first assistant output and at each append/checkpoint/sync/reopen edge. Assert exact ordered prior context, checkpoint and next request after restart. Inject create/write/sync/corruption failures; never report success or silently discard entries. Repeat historical I4 probe against the new seam.
3. **Prove SQLite/mail seam:** real SQLite, journal, router HTTP and direct handler; crash at acceptance, attempt reserve, append, ACK commit, result append and reply enqueue. Assert acceptance succeeds without transcript, ACK only with durable exact-session entry, one message/one reply, wrong-session rejection, uncertainty on ambiguous evidence. Test two interleaved senders, mixed tmux WebSocket traffic, fixed target, queue limits/expiry and duplicate IDs.
4. **Prove independent worker/tools/policies:** launch via root `mecha_worker` and direct router handler; worker gets own session/mailbox and can send/receive/reply; list/cancel/cleanup/result and restart/reset fences. Crash after worker creation before control result; one worker, no blind relaunch. Cover every approved tool/action, reminders, goals/snooze, indicators, manual/auto compaction and post-compaction notification, full and quiet/complete histories, UI reconnect/gap repair.
5. **Prove provider/isolation/rollout:** OAuth login/refresh/rotation and Codex Responses stream/tool fixtures; authorized available-model listing/selection, active/idle switch, stale/unauthorized selection, logout and restart. Inject agent panic, stuck tool, provider cancellation, memory/backpressure, router kill and cold recovery. Compare RPC and embedded contracts with deterministic fixtures, then opt in a few new roots; measure uncertainty, ACK lag and resource limits. Keep RPC rollback and tmux path until gates pass; do not migrate or delete sessions on rollback.
