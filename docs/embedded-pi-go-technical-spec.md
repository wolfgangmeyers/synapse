# Embedded Pi Go: technical specification

## Decision and boundary

Run a router-managed root and router-launched managed workers as **independent in-process Go sessions**. Each has its own persistent agent ID, mailbox, session/epoch, model, run generation, controls, and lifecycle. A worker is not a Pi child and is not a tmux window. Both use the same router queue, SQLite control records, managed HTTP routes, and live UI. The existing WebUI must work with zero WebUI code changes: preserve its HTTP/WebSocket APIs, fields, live snapshot/delta projections and behavior. Keep the existing RPC root and supervisor-owned tmux/WebSocket workers unchanged as rollback and mixed-mail paths. No recursive/native subagents in v1. No import of old Pi sessions, automatic tmux migration, TypeScript extension execution in Go, or speculative cross-runtime compatibility layer. RPC managed-worker parity is not a v1 requirement when it adds complexity; preserve named product capabilities and user-visible outcomes instead. Copy RPC patterns only when simpler, not its request states, extension hooks/event shapes, or incidental edge cases.

Only Codex OAuth and Codex Responses are in scope. No Google, Cursor, or generic API-key parity. An embedded runtime is opt-in per **new** root/worker. An existing RPC session remains RPC across restart; rollback does not reinterpret its transcript as a Go session. Do not call the replacement ready until all gates below pass.

## Durable state and receipts

Router SQLite is the only persistent conversation and control store for embedded agents. There is no separate Go/file session journal, path pointer, or cross-store reconciliation protocol. The existing SQLite mailbox and ACK semantics remain intact for RPC/tmux and mixed mail.

1. **Acceptance:** `/v1/messages` validates and commits a message ID, envelope, fixed destination when known, limits, expiry, and queued status in SQLite. Its success/acceptance ACK means *only* SQLite accepted mail. It does **not** wait for a conversation append, delivery, model turn, or reply. Duplicate ID plus identical envelope replays; conflicting content fails. Preserve the existing distinction for HTTP `202` launch: saved operation, not ready agent.
2. **Delivery:** Serialize direct delivery per agent. In SQLite, reserve a specific attempt bound to agent ID, session ID/epoch, run generation, message ID, and immutable append key. Transactionally insert the exact ordered mail entry and commit the **processing/delivery ACK** for that same attempt when possible; neither an entry ID nor `Run` success alone is an ACK. A failed transaction leaves both uncommitted. If reservation and append/ACK span transactions, recover from SQLite attempt and entry state using the stable key and content digest, without appending twice. Normal inbound UI prompts and control-result messages need the same durable conversation boundary before claiming delivery. Acceptance commit remains separate and does not wait for this step.
3. **Conversation authority:** Keep ordered SQLite entries per session/epoch for user, assistant, tool call/result, mail attribution, model changes, and compaction checkpoints, with stable sequence, parent/branch and checkpoint ancestry. A first prompt commits before assistant output. Commit each finalized entry before reporting append success, and load only a validated ordered projection on reopen. Check session binding, sequence/parent continuity, digest and checkpoint position. SQLite integrity failure, corrupt/missing entries, or broken checkpoint ancestry blocks resume and delivery: surface not-ready, preserve evidence, and require explicit repair or reset into a new epoch, never silent skip or fallback. Enforce bounded entry/blob sizes and retention; prune only entries not needed to reconstruct the active replayable context, checkpoint ancestry, unresolved attempts/operations, and required full-history views. If safe pruning cannot meet a limit, block new turns and report the limit rather than deleting needed context.
4. **Recovery and effects:** Reopen SQLite attempts, entries, ACK and operations together. An exact matching entry with a missing ACK may be ACKed transactionally without a second append; a proven unstarted attempt may be delivered. Corrupt, conflicting, or ambiguous evidence is **uncertain** and blocks automatic retry. An external tool/provider effect cannot join the SQLite transaction: persist a stable fenced operation ID and intent before invoking it, persist the immutable observed result before returning from the handler, and show unknown outcome on interruption. Never claim atomicity across that boundary or automatically replay an unknown effect; reconcile only when the outcome is provable. A checked SQLite tool-result conversation append must succeed before the next model request, or the turn fails closed.
5. **Interrupted-turn wakeup:** On unclean restart, restore only committed ordered entries and the validated compaction checkpoint; mark any open turn interrupted, not complete. In the existing SQLite per-agent turn queue, persist one non-mail recovery notice with a stable ID derived from agent ID, session/epoch, and interrupted turn ID (unique across repeated restarts). The notice names that turn and any tool outcome that remains unknown. Do not use `/v1/messages`, create a mail ACK/reply, resume partial tokens, or auto-repeat an uncertain external effect. After reopen, fence the old generation and its callbacks, validate the projection, then admit the notice on the serial turn lane under the current agent/session/epoch/generation. Transactionally append it once to conversation under its stable key and record its queue disposition; the agent's next model turn sees the notice in context. Persist a generation-bound start before that model call. On another crash, retry only a provably unstarted notice; an already-started wake turn is interrupted and never blindly re-run or turned into another recovery notice. Keep its interruption visible instead. Reset/terminate fences pending notices; old-epoch notices cannot enter a new session. This is an internal recovery turn, not ordinary user mail.
6. **Reply:** Bind final assistant output and settled status to the initiating turn ID and its original sender; ignore late events from another turn/generation. Queue one stable-ID auto-reply only after that turn settles and the result is durable. Streamed fragments are not replies. `mecha_mailbox_send` is a separately validated, correlated SQLite enqueue, never folded into auto-reply.

At pinned Pi Go revision `e6b56e7223cfab707b21a0a19e0a9a2417ac960a`, `coding/session.go`'s `LoadBranch` accepts a `BranchProjection` built from a session tree, not arbitrary ordered state plus checkpoint import/export. `LoadHistory` discards compaction. `Record` subscribes to message-end events; `coding/session_store.go`'s recorder delays the first write until assistant output and hides write/create failures, with no checked transactional recorder. `coding/compaction.go` publishes its checkpoint into in-memory state without a pre-publication persistence hook. The needed public seams are checked entry capture/append integration, validated projection/checkpoint construction and loading (or equivalent explicit import/export), and a pre-publication checkpoint commit hook that can fail closed. These are proposed SDK changes, not current APIs. The historical [`embedded-pi-go-i4m2-gate.md`](embedded-pi-go-i4m2-gate.md) demonstrates why the unchecked recorder cannot prove durability. It does **not** block SQLite mail acceptance; its old transcript-as-acceptance-receipt reading is superseded by the two ACK boundaries above.

## Lifecycle, tools, and status

- **Launch:** Reserve root/worker ID, canonical request hash, operation ID, requested model, cwd, session/epoch, and desired state in SQLite before constructing a session. Same `X-Request-ID` and body returns saved result; mismatch conflicts. One worker-launch control request maps to one durable worker record and unique identity, even if the router crashes after construction but before result delivery. On recovery inspect the record and generation before starting anything; unknown external completion is reported unknown, not re-executed. Enforce bounded agent count, pending work, turn queue, and per-turn deadlines. Worker list/send/cancel/cleanup/result operations use this independent identity and mailbox; parent relationship is metadata, not ownership of the worker's session. Parent restart/reset must not implicitly duplicate workers.
- **Start/restart/reset/terminate:** Restore desired agents after SQLite validation and attempt/operation recovery, then mark each ready only after model/auth, tools, history and checkpoint bind. Process pending interrupted-turn notices after reopen on the serial lane, never alongside the old turn. Keep saved launch/restart/reset/terminate outcomes, bounded retry/backoff, and old-run fences. Health may answer while recovery is running; normal managed traffic remains gated until startup repair, and an individual agent can remain not ready. Restart continues the same ordered session/epoch; reset cancels and fences pending callbacks, creates a **new** session/epoch, and does not inherit old conversation/compaction or re-inject mail from the old epoch. Terminate fences the run and stops new turns. Explicit cancellation/timeout never implies a completed external effect was rolled back.
- **16-tool embedded requirement:** Preserve these 15 revision-one tool names from `pi-extensions/mecha-rpc/manifest.ts`: `goal`, `goal_snooze`, `mecha_parent_message`, `mecha_mailbox_send`, `mecha_request_inline_tool_allowance`, `mecha_recall`, `mecha_context`, `mecha_state`, `mecha_priority`, `mecha_verification_handoff`, `mecha_reminder`, `mecha_worker`, `mecha_pr`, `mecha_git`, `mecha_router`. Checked-in revision-two `router/contract/managed-tools-v1.json` adds `web_search__4f4ca2a3ae8ea237531b8c5264d53d15474c0848fc8d7eeada0fef5b85b139ac` (`web.search`); the router's `internal/managed/manifest.go` and `root_control_handlers.go` validate this search operation. The existing RPC manifest also includes `mecha_settled_notifications`, but it is not required for embedded agents. Gate 1 must verify the named tools, required actions, argument validation, and search dispatch; exact RPC schemas and incidental edge-case behavior are not required. No phantom missing tool or additional dynamic installs. Install only this fixed host allowlist and separately approved built-in read/bash/edit/write permissions before the first model request, validate per-action inputs and caller fence on the host, and reject runtime-added executable tools. The current TypeScript supplemental-install mechanism is not a Go dynamic-tool requirement. At the pinned Pi Go revision, `AgentTool.Execute` returns the final `AgentToolResult` synchronously; the loop appends tool results before its next provider request, while `onUpdate` is progress only. For bounded embedded handlers independent of the calling Pi session/turn lane, return the direct router handler result from `Execute` in that turn instead of returning `queued` and later injecting a correlated RPC result. Preserve the existing RPC behavior. Persist the fenced operation intent before effects and immutable observed result before return; commit the checked SQLite tool-result append before another model request, failing closed on append failure. Never automatically replay an unknown effect; reconcile only from provable evidence. Truly long-lived actions return a durable operation ID and status, not fake completion. Defer self-reentrant actions (including manual compaction) to a safe turn boundary. A parallel tool batch may have concurrent effects, but results must be durably appended in deterministic call order before continuation; cancellation fences new starts and cannot claim an already-started effect was undone. Reconcile worker state on interrupted launch; unknown effects stay visibly unknown.
- **Policy/features:** Preserve goal status/set/off, snooze limits/budget/refill and evaluator wakeups, reminders and verification handoff, inline-tool allowance, recall, `mecha_context` manual/automatic compaction and post-compaction handoff. Persist the actual compaction checkpoint before projecting success; preserve context/history order after restart. Support full transcript and bounded quiet/complete history as separate views. Indicators (turn, tool, compaction, goal/snooze, worker, auth/model) come from current fenced session events plus durable router state. Publish a fresh authoritative snapshot on reconnect and ordered versioned deltas; drop late generation events, repair gaps from snapshot, never infer a worker or completion from streamed text. Do not show ready if auth, SQLite conversation, or checkpoint cannot reopen.
- **In-process failure domain:** Recover panics at each agent/turn/tool boundary and record agent failure without crashing a healthy router where possible; process-wide faults still take down the router. Bound concurrency, memory pressure, output size, tool execution, and provider streams. Apply context cancellation; when a call does not cooperate, make it observable that no unsafe replacement turn overlaps its effects and that unknown external effects are not blindly replayed. The mechanism need not be quarantine or refusal until resolution. Startup must treat an unclean process exit as possible interruption, not proof of safe retry. No claim of OS-level isolation.

## Codex login, model selection, and security

The router already owns provider-auth operations and their non-secret status projection for the RPC path. Implement Codex-only embedded login/prompt-response/logout through the existing `/v1/provider-auth` route family; do not assume the current helper is an embedded Go OAuth integration. Complete authorization with bounded state/PKCE and prompt lifetime, validate callback/response binding, cancel cleanly, and never publish codes or tokens. The requirements exclude secrets from SQLite and browser status. For the embedded path, choose owner-only protected durable credential storage outside SQLite and serialize refresh and login/logout per provider; this storage layout is a proposed implementation, not an existing Go integration. Write rotated secrets atomically (temporary file, sync, rename, parent sync), and commit before use/publication so a restart cannot resurrect a spent refresh token. Failed refresh leaves auth unavailable with a safe status; never print tokens in logs, UI, history, errors, or tool output. Codex Responses streaming must carry tool-call IDs/arguments and final outcomes correctly, honor cancellation/retry policy, and use refreshed OAuth credentials for each request without leaking them.

Keep the shared `GET /v1/models` and provider-status RPC-visible behavior for existing consumers. Apply Codex OAuth filtering and auth-revision validation to embedded agent model listing and selection without narrowing those shared projections. The router model catalog/selector (`internal/managed/models.go`) owns validation and persistent default/agent selection; no unconditional hardcoded fallback to an unauthorized or stale model in the embedded path. Reject unavailable, stale, signed-out, or wrong-provider selections at launch, default update, active change, and restart. Persist selected provider/model and project it through managed HTTP and UI-live. For an idle agent, switch before its next turn. For an active agent, serialize the change at a turn boundary (or explicitly cancel and fence the old turn); atomically record the operation and selected model only after the live session confirms the new selection. On restart revalidate against refreshed OAuth-filtered catalog and keep the agent not ready if its saved selection is unavailable rather than silently substituting one. Test refresh, login/logout, revision races, active/idle changes, and restart using the real provider request boundary, not only catalog rows.

Keep working-directory/project trust, tool permissions, command/path restrictions and manifest bounds at least as restrictive as the current managed runtime. Existing managed HTTP controls have no authentication (`router-architecture/architecture.html`): CORS/Origin is not authorization. Limit listener/network access to trusted clients, do not broaden exposure, and treat root/worker IDs and UI status as non-secret but not authority. No caller-chosen tool list or model provider bypass.

## Implementation gates and verification plan

These are required **future** gates, not tests performed by this document.

1. **Freeze contract/build:** verify the 15 required revision-one tools plus revision-two web search (excluding `mecha_settled_notifications`) for required actions and validation, approved built-ins, Codex model/filter policy and worker identity/UI outcomes. Record the audited SDK revision and reproducibly build the router with a supported compatible toolchain and dependency strategy. Confirm no old-session migration or new worker tmux launch is needed.
2. **Prove SQLite conversation and SDK seams first:** fake model, real Pi Go session and SQLite projection; crash before first assistant output and at each transaction, checkpoint publication, and reopen edge. Assert exact ordered prior context, checkpoint ancestry, and next request after restart. Inject commit, disk-full, integrity and corrupt-entry failures; never report success or silently discard entries. Test size/retention limits without pruning replayable context or required history. Repeat the historical I4 scenario against the new seam.
3. **Prove SQLite/mail seam:** real SQLite, router HTTP and direct handler; crash at acceptance, attempt reserve, transactional append+ACK, tool intent, external effect, observed result, checked tool-result append and reply enqueue. Assert acceptance succeeds without conversation append, ACK only with committed exact-session entry, one message/one reply, wrong-session rejection, and uncertainty on ambiguous external effects. Crash before/after notice creation, append, and wake start; assert one stable notice across repeated restarts, fenced delivery after reopen, no mail ACK/reply for it, and no duplicate model turn or external effect. Test two interleaved senders, mixed tmux WebSocket traffic, fixed target, queue limits/expiry and duplicate IDs.
4. **Prove independent worker/tools/policies:** launch via root `mecha_worker` and direct router handler using the same in-process runner type as root; worker gets own session/mailbox and can send/receive/reply; list/cancel/cleanup/result and restart/reset fences. Crash after worker creation before control result; one worker, no blind relaunch. Cover every approved tool/action, reminders, goals/snooze, indicators, manual/auto compaction and post-compaction notification, full and quiet/complete histories, UI reconnect/gap repair.
5. **Prove provider/isolation/rollout:** OAuth login/refresh/rotation and Codex Responses stream/tool fixtures; authorized available-model listing/selection, active/idle switch, stale/unauthorized selection, logout and restart. Inject agent panic, stuck tool, provider cancellation, memory/backpressure, router kill and cold recovery. Verify named product outcomes with deterministic fixtures (using RPC as a reference only where helpful), then opt in a few new roots; measure uncertainty, ACK lag and resource limits. Keep RPC rollback and tmux path until gates pass; do not migrate or delete sessions on rollback.
