Future option / not an implementation report

Could a Go-based Pi runtime replace the current Pi process?

This is an idea to evaluate, not an implementation. This page does not identify a specific pi-go repository or prove that one can replace Pi. Today the Go router starts a separate Pi process and talks to it through JSON-RPC messages.

The linked research covers Pi RPC, not pi-go. It tested Pi 0.85.0, so its findings may not hold for a newer version. The local pi --version check reported 0.87.1 on 2026-09-26. Check the actual installed runtime before deciding to replace it. RPC_RESEARCH.html:172-189 · RPC_IMPLEMENTATION_PLAN.html:13-28 · RPC_SPEC.html:307-328

01

The boundary today

This section describes current code. The linked requirements describe intended behavior; they do not prove every feature is implemented.

Current code

Direct process

The router's manager saves an agent and Pi session record, then starts a separate Pi process. It passes --mode rpc and specific extension file paths to that process.

router-proxy/internal/managed/supervisor.go:361-482, 489-550 · router-proxy/internal/managed/process.go:61-63
Current code

Router authority

The router accepts direct HTTP requests to start, restart, reset, or stop managed agents, and to read history, list models, or manage provider login. Its control boundary is network access: a client that can reach these routes can request these actions. This HTTP handler does not check a user session, browser origin, or login before dispatching them. Do not expose it to untrusted clients. The linked handler shows the current routes; older plans may differ.

router-proxy/internal/transport/managed_http.go:33-117
Research limit

RPC is not a generic host API

The cited research found that the tested Pi RPC interface could not register new model-callable tools from its controller or change provider credentials. It also could not give a trusted account of which child agents are running. The Pi extension and router bridge supply some of these functions. Recheck these limits against any runtime considered for replacement.

RPC_RESEARCH.html:231-270, 283-285, 374-385
02

Contracts a replacement must keep

The linked requirements and specification state what a replacement should preserve. They are design targets, not proof that every behavior works today.

Identity and recovery

Stable managed agent

A replacement must keep each agent's saved identity and conversation across restarts. It must support a deliberate conversation reset and recover from crashes without unlimited retries. The router tracks a run identifier, session version, and approved tool-list hash. It checks these values to reject late actions from an older run. Keep those checks until tests prove an equivalent safeguard.

RPC_REQUIREMENTS.html:284-301 · RPC_SPEC.html:366-381 · supervisor.go:401-482
Tools and authority

Same behavior, guarded calls

A replacement must offer the same approved list of tool names and argument formats. The router must check arguments and decide who sent a request from its own records, not from a caller's claim. Tool definitions must stay fixed during a session. Control requests must carry the current run's identity so an old run cannot act. Pi's coding tools and rules for child agents are separate from router control tools.

RPC_REQUIREMENTS.html:223-267, 312-333 · RPC_SPEC.html:329-357
Messages and UI

Same observable worker

A replacement must save mail until delivery and record when it is accepted. It must exchange messages with tmux workers and keep both the full conversation and the shorter history that omits noisy internal events. The UI needs a current list of parent and child agents plus updates tied to the current run. Terminal output alone cannot reliably say which child agents are active.

RPC_REQUIREMENTS.html:302-321, 335-351 · RPC_RESEARCH.html:325-383

Proposal: write tests for these behaviors that can run against either runtime before changing production code. A changed message order, saved session format, or visible tool result changes the user-facing behavior and needs explicit review.

03

What could change, and what stays

Possible simplification

Remove a transport layer

If a specific Go runtime can run Pi sessions inside the router while preserving extensions, tools, events, and saved conversations, the router might stop launching Pi subprocesses and exchanging JSON messages over their input and output. No such capability has been verified here.

Present subprocess boundary: process.go:61-63, 183-194 · RPC_SPEC.html:307-328
Still required

Router state and controls

Running Pi inside the router would still require SQLite records, safe handling of repeated requests, mail and history storage limits, and checks on who sent a request. The router would still need to reject late actions from old runs, recover after crashes, and send current state to the browser.

RPC_SPEC.html:307-357 · router-proxy/internal/store/managed.go:676-704, 893-900 · managed_http.go:33-117
New risk

Shared failure domain

Running Pi inside the router could make a Pi crash take down the router too. Today Pi runs as a separate process the manager can stop. Test crash isolation, upgrades, and resource limits before switching.

process.go:183-194, 287-401 · RPC_SPEC.html:366-381
04

A limited replacement plan

Proposal: keep the router's HTTP routes, saved records, and request rules. Put the proposed Go runtime behind the code that starts agents and receives their events. Keep tmux workers on their current path.

  1. 01 / CharacterizeFreeze observable behavior

    Write tests for startup, tool requests, mail, conversation history, child agents, restart, and reset using today's Pi process. These tests have not been run as part of this proposal.

  2. 02 / Try locallyEvaluate a specific Go runtime

    First identify a specific Go runtime. Use a fake model service with fixed replies. Check tool arguments, event order, saved conversations, who may send control requests, and child-agent updates before connecting it to production code.

  3. 03 / ConnectConnect the new runtime to the router

    Keep the router's checks before requests run and its saved records. Link new runtime events to the current agent run and to receipts proving that results reached its saved conversation. Try this path with selected test agents only.

  4. 04 / CompareTest before wider use

    Proposed tests: restart agents and the router, send late events from old runs, repeat a message, and exchange mail with tmux workers. Keep the current Pi process path available if the new runtime behaves differently.

Current seams: supervisor.go:361-482, 489-550 · process.go:61-63, 183-194. Steps above are proposals.
05

Proof gates and open questions

Gate / proposed

Tool and result behavior

Proposed test: confirm the model sees every required tool and its argument limits before its first reply. Make a real router control request and check its later result. Check what the model sees when a result is immediate, delayed, or canceled. These checks have not been proved for a Go runtime.

Contract: RPC_REQUIREMENTS.html:223-267, 312-333 · prior isolated proof limit: RPC_RESEARCH.html:269-285, 295-323
Gate / proposed

Crash recovery

Proposed test: stop the runtime and router before and after accepting a request, adding its result to the conversation, and finishing the agent turn. Check that restart keeps the saved conversation, old runs cannot make changes, and a repeated request does not run twice.

Contract: RPC_SPEC.html:366-381 · current operation lookup: managed.go:893-900
Gate / proposed

UI and tmux workers

Proposed test: check the UI's agent list on first load and reconnect, then watch parent and child agents change state. Exchange mail with a tmux worker. Compare the full conversation and the shorter, less noisy history against the current Pi process path.

Contract: RPC_REQUIREMENTS.html:207-222, 302-321, 335-351 · evidence limit: RPC_RESEARCH.html:325-385

Questions before a decision

Which pi-go project and version would we test? Can it read existing Pi conversation files and run the required extensions and child-agent support? Which component handles provider credentials and the list of available models? Can a Pi crash leave the router running? The cited Pi RPC research does not answer these questions.
